# SBDB: Git Is the Audit Log

> Git is already an append-only ledger of every change you ever made — `sbdb events emit` projects it as a JSONL stream and stores zero new bytes.

Every team building auditable knowledge ends up writing the same dead-end service: an "events" table, a worker that watches for changes, a fan-out to Slack/Jira/SNS, and three months later the table is the source of truth instead of the docs. `sbdb` takes the opposite turn — git is already an append-only ledger of every change you ever made, signed by committer, ordered by time, immune to silent rewrites. `sbdb events emit <from> <to>` *projects* that history into a JSONL stream on stdout, ready to fan out to whatever downstream needs it, and stores zero new bytes.

The mechanic is one command that walks `git log <from>..<to>` over the docs directory, classifies each touched file by entity, and emits a typed event per mutation — and because nothing is stored, replays are deterministic, history is reorderable, and the schema for events lives in your schema's `x-events` block.

## The Audit-Log Anti-Pattern

Sit through enough architecture reviews and you will watch the same diagram drawn for the fifth time, with a fresh whiteboard and a new senior engineer wielding the marker. The application writes to its primary store. It *also* writes to an `events` table. A worker — usually a thing called `audit-relay` or `ledger-fanout` or, on one memorable occasion, `Mr. Audit` — watches that table and copies each row onto a queue. Downstream consumers (Slack, Jira, SNS, the data warehouse, the compliance bucket) read from the queue. The diagram is always neat. The reality is never neat.

> Every "audit log" service starts as an honest projection of the truth and ends as a second truth nobody can reconcile with the first.

Within a quarter, the `events` table has drifted from the rows it was supposed to mirror. Somebody wrote directly to the table from a backfill script. Somebody else fixed a typo in production without emitting the event. The worker fell behind for forty minutes during a deploy, and the engineer who knew it had fallen behind has since left the company. The diagrams still get drawn, but now they have asterisks. *We believe this is the order in which things happened.* You will hear the word *believe* a lot at the post-mortem.

The deep problem is not the architecture — it is the *premise*. The premise is that auditability requires another store. The thing you already have, the thing every committer in your repo touches every day, the thing whose entire purpose is to be a tamper-evident hash-chained ledger of writes by signed authors in deterministic order — that thing was sitting right there, and you spent six engineer-weeks writing a worse version of it. Worse, because the new store has none of the guarantees the original one already had: no hash chain, no parent linkage, no signature on the row, no replication built into the tool. You bought yourself a queue and called it a ledger; the regulator, when they finally arrive with questions, will not be fooled.

The cost is rarely the worker itself. The cost is the *fear* the worker accrues over years — the fear that the table and the rows have diverged, that the diff you are looking at in the post-mortem is half-truth, that the answer the auditor wants is not the answer the table is going to give. That fear is what `sbdb` deletes.

## Git, Read As a Ledger

Read your repo's history the way an event-sourcing zealot would read it. Each commit is a *transaction*. Its parent hash is the *previous offset*. The committer's signature is the *actor identity*. The commit message is the *event metadata*. The tree diff is the *payload*. Nothing on that list is something you have to build — it is already there, already serialised, already replicated to every clone of the repo, already signed (if you have signed commits turned on, which you should), already immune to silent rewrites because the moment somebody alters a past commit, every descendant's hash changes and the chain visibly breaks.

The honest aside, because this article is not selling you a religion: git is *not* a real-time message bus. Latency is measured in pushes, not milliseconds. You do not get exactly-once delivery semantics for free. You do not get per-consumer offsets the way Kafka would give them to you. What you get is *the property that matters for audit*: append-only, ordered, signed, and free. For knowledge bases — where the meaningful event rate is "tens to thousands per day," not "tens of thousands per second" — that is exactly the right trade.

## The Projection Model

`sbdb events emit <from> <to>` is a thin walker around `git log`. Internally, the algorithm is:

1. Resolve `<from>` and `<to>` to commit SHAs in the docs repo.
2. For each commit in the range, list the files in the diff.
3. For each touched file under the docs root, look up its entity (`notes`, `adrs`, `runbooks`, …) by matching against the schema's path glob.
4. Classify the change: created, updated, archived, renamed.
5. Emit one JSONL line per (commit × entity-change), shaped by the entity's `x-events` block in the schema, written to stdout.

There is no daemon. There is no queue. There is no offset state kept anywhere except in your own consumer — which is exactly the point. If you run the command twice with the same `<from>` and `<to>`, you get the same bytes on stdout, in the same order, every time. *Deterministic given the same git history* is precisely what "immutable" means in practice; the property the second part of this series called out as the deep guarantee of `sbdb` is what makes the audit-log projection trustworthy here.

> A stateless projection is the only audit log that cannot lie to you about itself — because it has nothing of its own to lie with.

That property is also what lets you replay. The classical audit service has one timeline: the one that happened. Replays mean "drain the events table again," which is a coin flip on whether the consumer is idempotent. With `sbdb events emit`, replay is just calling the command with a different range. Yesterday's compliance report, last Tuesday's incident review, the week of the regulator's window — each is a separate `<from>..<to>` invocation against the same git history, each producing exactly the JSONL that range deserves, regardless of how many times you've run it before.

## The `x-events` Schema Block

The shape of the JSONL is not invented by `sbdb`. It is declared per-entity in the schema's `x-events` extension, alongside the `x-virtuals` and `x-refs` blocks from the earlier parts of this series. The schema owns the contract; the CLI is just the projector.

```yaml
x-events:
  emit:
    created:
      type: note.created
      include: [id, title, author, tags, created_at]
    updated:
      type: note.updated
      include: [id, title, author, tags, updated_at]
      diff: [title, tags, status]
    archived:
      type: note.archived
      include: [id, title, archived_at, archived_by]
    renamed:
      type: note.renamed
      include: [id, old_path, new_path]
```

Each child of `emit` corresponds to one of the change classes `sbdb` already detects. `type` is the event type string that downstream consumers route on. `include` is the whitelist of frontmatter fields copied into the event payload (so `body` never leaks into your audit bus by accident). `diff` is optional — when present, the event also carries a `changed: [...]` list naming which of those fields differed between the two commits, the closest thing to "what did this commit do" you can get without re-running the markdown parser downstream.

A concrete event looks like this:

```json
{"type":"note.updated","id":"adr-0042","author":"jdoe","timestamp":"2026-05-17T14:21:08Z","sha":"a1f0c4d","changed":["status","tags"],"trace":"docs/adrs/0042-stop-doing-x.md"}
```

Seven fields, all primitive, all derived from frontmatter or git. No body, no embeddings, no opinion. The consumer decides what to do with it; the projector decides nothing. That separation is deliberate: the schema author owns *what is an event*, the operator owns *where the events go*, and the CLI is the boring pipe between them. When a new entity type lands in the docs repo — a new ADR class, a new postmortem template — adding it to the audit stream is one block of YAML, not a deploy of `audit-relay`. The first time you ship a new entity end-to-end without paging anyone, the model has paid for itself.

## Pipelines That Fit on a Postcard

The point of stdout is that every Unix tool already knows how to read it. The three pipelines below are the patterns we keep seeing in the field; each is one line of shell.

**SNS fan-out**, run from CI on `git push`:

```bash
sbdb events emit HEAD~10 HEAD | jq -c . | while read -r line; do \
  aws sns publish --topic-arn "$DOCS_TOPIC_ARN" \
    --message "$line" --message-attributes '{"type":{"DataType":"String","StringValue":"docs-event"}}'; \
done
```

`HEAD~10..HEAD` covers the typical merge window; rerun with a wider range during a backfill. The `jq -c` is paranoia about preserving compact JSON; `sbdb` already emits one-line JSON, but downstream tools occasionally pretty-print and you'd rather not debug that at 3 a.m.

**Slack webhook**, the same shape: `sbdb events emit <range> | jq -r '"<\(.trace)|\(.id)>: \(.type) by \(.author)"' | xargs -I{} curl -X POST -d '{"text":"{}"}' "$SLACK_HOOK"`. Five seconds of effort per channel.

**Cron-replay on tag**, the compliance pattern: every Monday, a CI job runs `sbdb events emit $(git rev-list -n1 'last-week') HEAD` and dumps the result into the regulator's bucket. The week before, the auditor asked for the same range; you ran the same command and got the same bytes. The auditor stops asking *whether* anything was edited because the answer is mechanically derivable.

A consumer-side example in Python, suitable as a Lambda or a one-off script:

```python
import json, sys

ROUTES = {
    "note.created":  lambda e: print(f"[+] {e['id']} by {e['author']}"),
    "note.updated":  lambda e: print(f"[~] {e['id']} changed: {e['changed']}"),
    "note.archived": lambda e: print(f"[#] {e['id']} archived"),
    "adr.created":   lambda e: notify_slack(e),
}

for line in sys.stdin:
    event = json.loads(line)
    handler = ROUTES.get(event["type"])
    if handler:
        handler(event)
```

Pipe `sbdb events emit` into that script and you have, in fifteen lines, the entire core of an audit relay. The remaining ninety percent of a typical "audit service" — the table, the worker, the retries, the dashboards that watch the worker — disappears because nothing of it was load-bearing once the projection became the truth.

## Replay: The Property No Log Service Has

Pin the previous section in your head and look at it from a different angle. If the projection is deterministic, then any historical window can be re-derived on demand. Not "queried from the archive" — *derived*. The same command, the same range, the same bytes. This is what makes the model fundamentally different from any audit service that retains its own events: the audit service has a *recording* of the past; `sbdb` has a *function* over the past, and a function is something you can call again.

What this changes for the engineer on call: when the compliance team comes asking for the events between two dates, you don't dig through an archive. You run a command. When the incident review asks *what changed in the runbook between the deploy and the page*, you don't grep a queue. You run a command. When a regulator asks the same question six months later, you run the same command and you know — not believe, *know* — that the answer is the same bytes you produced the first time. The audit log stopped being a thing you store and started being a thing you compute.

## What This Future Looks Like

Picture the team that internalises this. They stop drawing the audit diagram on whiteboards because the diagram has only one box on it. There is no `events` table to argue about. There is no `audit-relay` to alert on. The compliance bucket fills itself from a cron job that runs nine seconds a week. When the regulator's window arrives, somebody runs `sbdb events emit | tee | aws sns publish` in CI and goes back to lunch. The audit work that used to consume a quarter consumes a coffee.

That's the lift. Not the cleverness of treating git as Kafka — git is not Kafka and never will be — but the discovery that the audit service you were planning to build was a *projection of a thing you already had*, and now you can stop building it. The engineering hours you were going to spend reconciling drift between the events table and the rows it was mirroring are hours you spend on the next interesting problem instead. The team that runs `sbdb events emit | tee | aws sns publish` in CI stops building audit services and starts treating git the way the rest of the industry treats Kafka — as the bus that was already there.
