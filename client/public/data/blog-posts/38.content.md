# SBDB: Your Markdown IS Your Database

> Markdown files are structured data wearing prose's clothes. `sbdb` is the smallest tool that lets you stop pretending otherwise.

Your knowledge base is a database. You just refused to admit it, and now you have a 4,000-file `docs/` directory that nobody trusts. `secondbrain-db` is the tool you write the moment you stop pretending markdown is text — typed schemas, integrity signing, a knowledge graph, and git as the audit log, all in a single Go binary that gets out of your way when you don't need it.

This first part is the head-change. Markdown files are structured data wearing prose's clothes — once you accept that, `sbdb` is the smallest tool you can layer over the directory without giving up the markdown itself. Everything else in the series is detail on the five layers.

## The Mindset

Open any ADR in your repo right now. What do you see at the top? A YAML block — `status`, `date`, `owner`, `supersedes`. Below it, prose. Inside the prose, a handful of `[[wikilinks]]` or relative `[markdown](./other-decision.md)` references to sibling documents. At the bottom, maybe a "Related" section listing three more files by name.

That document is a row in a database. The frontmatter is the typed columns. The body is the payload. The links are the foreign keys. You write SQL against this shape every time you grep for "status: accepted" or run a script that walks the `docs/` tree counting orphans. The schema exists; it's just enforced by nobody.

> A wiki is a database where every constraint is a vibe.

The mental shift is small but load-bearing. Once you say *"this is a database table"* out loud, every problem you have with the knowledge base reclassifies. The doc with `staus: accpeted` is a typo bug *and a missing CHECK constraint*. The dangling `[[ADR-0042]]` is a broken link *and a referential-integrity violation*. The intern who edited eight pages overnight is a teammate *and an uncontrolled writer with no audit log*. Every one of those problems has a known shape in database engineering. The directory is a database that has been waiting for you to treat it like one.

## The Four Quiet Ways It Rots

A small markdown directory is fine. The trouble starts somewhere between months four and six, when the file count crosses a thousand and the first contributor leaves. The rot is never loud — it arrives as four quiet failure modes, each individually survivable, collectively fatal.

**Frontmatter drift.** Half the files use `tags:`, the other half use `keywords:`, and the AI assistant that touched 400 of them last quarter invented `topic:` because it had never seen this codebase before. `grep` lies about your tag taxonomy because there is no taxonomy, only convention.

**Silent edits.** Someone — agent, intern, well-meaning future you at 1 a.m. — rewrites a paragraph in a decision document and pushes it as a typo fix. No reviewer notices the semantic change. Three months later, a production decision rests on the new wording and nobody remembers it was ever different.

**Link rot.** A document is renamed; eighty-seven references to it become 404s the next time someone clicks. Nothing failed loudly. The links just stopped meaning what they used to mean. By year two, your "Related" sections are dishonest in a way the directory cannot detect on its own.

**Inventory loss.** You can no longer answer simple questions about your own knowledge base. *How many runbooks do we have? Which ADRs are still in `proposed` state after six months? Who owns the four documents tagged `deprecated` but still linked from onboarding?* The answers exist somewhere in the file tree. Surfacing them requires writing a script every time, because there is no index.

The deeper failure is institutional, not technical: the team stops trusting the docs. Once trust drops below a threshold, contributors stop reading them, then stop writing them, and the knowledge base becomes the corporate equivalent of a basement nobody wants to enter. The files are still there. They just don't count any more.

## What `sbdb` Adds, In One Paragraph

`secondbrain-db` is a static Go binary that turns a directory into a database without taking the directory away from you. The directory still has `docs/`, your editor still opens markdown, git still tracks the files. `sbdb` adds five things alongside the markdown: a `schemas/` directory that declares your types (JSON-Schema 2020-12 plus a small set of `x-*` extensions), `.sbdb/` sidecars next to each document that hold integrity hashes and computed fields, a local SQLite index that answers queries fast, and a thin event projection on top of `git log` that lets you treat history as a typed JSONL stream. The runtime contract is a single binary with a stable JSON CLI. That's the whole system.

The directory is the floor. The lattice is what `sbdb` builds on top — five thin layers that turn unreliable convention into enforceable contract, without ever touching the markdown the writer cares about.

## The Five Features At A Glance

**Typed schemas.** Schemas live in `schemas/*.yaml` as JSON-Schema 2020-12 documents, with a few `x-*` extensions that tell `sbdb` how each schema maps to the filesystem (`x-storage.path`, `x-storage.filename`), how identity works (`x-entity`), and what integrity guarantees apply (`x-integrity`). Validation runs on every `sbdb create` / `sbdb update`, and on demand across the whole directory via `sbdb doctor`. The frontmatter your editor already shows you is now a contract instead of a hint.

```yaml
# schemas/notes.yaml
$id: https://sbdb.local/schemas/notes
x-entity: note
x-storage:
  path: docs/notes
  filename: "{{ slug }}.md"
x-integrity:
  algorithm: sha256
type: object
required: [title, status]
properties:
  title:  { type: string, minLength: 1 }
  status: { type: string, enum: [draft, active, archived] }
```

**Integrity signing.** Every managed document gets a `.sbdb/<name>.json` sidecar with a `sha256` of the canonical content. Edit the file with your editor, run `sbdb doctor`, and you see exactly which documents were hand-modified since the last managed write — no false positives, no whole-repo diffs. The sidecars are boring, deterministic, diff-friendly. They are also the thing that lets you trust an AI agent with write access to the directory, because *you can see what it changed*. Part 3 unpacks this.

**Virtual fields.** Some properties are not in the frontmatter and never should be — `word_count`, `last_modified_by`, `referenced_count`, "is this past its review date." Virtual fields are small Starlark functions declared in the schema; `sbdb` runs them in a sandbox at query time and caches results in the sidecar. You get computed columns without touching the markdown body. Part 4 shows what survives the sandbox and what doesn't.

**Knowledge graph.** Links between documents (`[[wikilinks]]`, relative `.md` paths, explicit `refs:` arrays in frontmatter) are extracted into a SQLite-backed graph on every write. The graph answers the questions a file tree cannot: *what links to this? what does this transitively depend on? which nodes are orphans?* Foreign-key constraints are enforced — link to a slug that doesn't exist and `sbdb` says so. Part 5 walks the schema.

**Audit-log-as-projection.** Git already records who changed what, when, why. `sbdb events emit` projects the git log into a typed JSONL stream: one line per managed change, with the entity name, the diff of frontmatter, the new hash, and the commit metadata. You don't run a separate audit subsystem; you run `git log` through a typed lens. Part 6 plugs that stream into a tail-able event feed.

## The Shape Of The Binary

`sbdb` is one static Go binary. No daemon, no server, no `init` ceremony — point it at a directory with a `schemas/` folder and it works. The CLI is JSON-in / JSON-out by default, with a stable schema for stdin and a stable schema for stdout, because the design assumption is that *the primary user of `sbdb` is probably not a human*.

```bash
echo '{"title":"Postgres tuning","status":"draft"}' \
  | sbdb create --schema notes --slug postgres-tuning
```

That one command validates the input against `schemas/notes.yaml`, writes `docs/notes/postgres-tuning.md` with the frontmatter and an empty body, computes the integrity hash, updates the sidecar, indexes the row in SQLite, and prints a single JSON line describing what happened. Failures exit non-zero with a structured JSON error on stderr. The contract is exactly as boring as you want a contract to be.

```bash
sbdb query --schema notes --filter status=active --format json
```

Returns a JSON array of matching rows, each with frontmatter, computed virtuals, integrity status, and a path to the source file. Same shape every time. Easy for a script, easy for an LLM agent, easy for a human reading it once.

The design point worth noting: there is no `sbdb serve`. No socket, no daemon, no port to forget about. The next call starts the binary, reads the directory, does the work, and exits. That makes it trivially scriptable, trivially containerizable, and trivially honest about its state — the state is the directory and the SQLite file, not a long-running process.

## What You Give Up

Honest accounting, because the rest of the series is more fun if we put the costs on the table early.

You give up *unstructured freedom*. The first time a schema rejects a frontmatter typo, you'll be annoyed. The first time it catches the same typo before it ships, you'll be glad. The trade is permanent — `sbdb` is a tool that occasionally tells you "no", and a system that never tells you "no" is also a system that never tells you anything.

You give up *clean diffs*. The `.sbdb/` sidecar directory shows up in `git status` every time you touch a managed document, and reviewers have to learn to scroll past it. The information density of the sidecar is high, but it isn't beautiful.

You give up *a Starlark function that will, eventually, surprise you*. Virtual fields are tiny computations; they are also code, and code drifts. Part 4 spends time on the failure modes — sandbox limits, deterministic execution, what happens when a virtual references a frontmatter field that no longer exists. The fix is straightforward; the surprise is real.

> A schema you can edit is not a cage. A schema you cannot edit is not a database.

What you don't give up is the markdown. The files are still files. You can open them in any editor, on any machine, with or without `sbdb` installed, and they read like the documents they are. `sbdb` is an *opt-in* layer — delete the binary tomorrow and the directory remains a normal repo of normal markdown. That symmetry is the whole point.

## What This Lets You Stop Worrying About

The team that gets this right stops fearing the moment their `docs/` directory crosses a thousand files. Each new document arrives as a typed row, with a hash, a place in the graph, and a future event in the audit log — and the directory just keeps absorbing them. The AI agent rewriting half the docs at 3 a.m. is no longer the thing that wakes anyone up; the hashes catch what it touched, the schema catches what it broke, the graph catches what it orphaned, and a human reviews the projection in the morning over coffee.

A knowledge base that holds itself together is a strange feeling at first. The directory stops being a basement and starts being a workspace. Contributors begin writing again because writing now counts — every doc has the same guarantees as a row in a real database, and the guarantees travel with the file. The rest of the series is just five thin tours of the lattice: Part 2 starts with the schema, because the schema is the contract every other layer leans on.
