# SBDB: Typed Schemas

> A copy-pasteable JSON-Schema 2020-12 contract for every markdown file in your repo, plus the small `x-*` vocabulary that turns the schema into an ORM.

A frontmatter field with no schema is a bug waiting for a quiet Tuesday. `sbdb` puts a JSON-Schema 2020-12 contract behind every markdown file in your repo — and the contract is editable, lintable, and self-documenting to your IDE the moment you save it. Stock validators (`ajv`) accept the schemas; `yaml-language-server` autocompletes your frontmatter; and the only sbdb-specific magic lives behind one prefix you can grep for: `x-`.

Once you have a schema, four things become free that used to be a quarterly cleanup project — type validation, default values, foreign-key references, and an editor that yells at you the moment you write `status: actve`. That is the whole pitch for this part, and the rest of the article is just the receipts.

## Why Schemas Are the Load-Bearing Feature

Part 1 made the case that a markdown directory is a database in denial. The schema is the moment the denial ends. Everything else `sbdb` ships — the integrity hashes, the Starlark virtual fields, the knowledge graph, the git event log — is built on top of the assumption that *this file has a known shape*. Strip out the schema and the rest collapses into "well, we hope this field is a date."

The mental flip is small but load-bearing. You stop treating `frontmatter` as a freeform key-value bag that some humans happen to fill in, and start treating it as the typed *header* of a typed *record*. The body of the markdown is the long-form payload. The links inside the body are foreign keys waiting to be extracted. The schema is the table definition. There is no migration to run, no Postgres to provision; the contract lives in a YAML file next to the docs and the validator runs in 12 milliseconds.

> A schema doesn't make your docs *better* — it makes them *negotiable*. You can now have an opinion about a field at PR review time, instead of finding out in production that three teams spelled `priority` four different ways.

The thing schemas buy that nothing else does is **vocabulary discipline at the moment of writing**. The author doesn't discover the field is wrong six months later when a dashboard breaks. The editor underlines `status: actve` on the keystroke that produced it, because `yaml-language-server` has already read the schema and knows the only valid values are `draft`, `active`, and `archived`. The error happens at the place and time where fixing it is free. That is the whole win, in one sentence.

## JSON Schema 2020-12 in One Paragraph

If you have seen JSON Schema before, almost everything you remember carries over. `sbdb` standardises on draft `2020-12` — the current published draft, with `$ref` resolution, `unevaluatedProperties`, and the cleaned-up vocabulary keywords. The shape is still the one you know: a top-level object with `$id`, `$schema`, `title`, `description`, then `properties`, `required`, `additionalProperties`. Each property is itself a schema with a `type` (`string`, `number`, `boolean`, `array`, `object`, `null`), and the usual narrowing keywords on top — `enum`, `format`, `pattern`, `minLength`, `minimum`, `items`, `$ref`. If you have written a Pydantic model or a TypeScript interface, the cognitive distance is roughly one cup of coffee.

What `sbdb` adds is a small extension vocabulary under the `x-` prefix — the standard JSON Schema escape hatch for vendor keywords. `ajv` ignores them by default. `yaml-language-server` ignores them too. Your IDE keeps autocompleting. `sbdb` reads them and uses them to wire the file into the broader system. The prefix is the contract: anything starting with `x-` is sbdb-specific, anything else is plain JSON Schema, and the two never collide.

## A Full Schema for a Small Entity

Here is the entity you'd write on day one — a `recipes` collection from the `sbdb` README, with every part of the contract visible:

```yaml
$schema: https://json-schema.org/draft/2020-12/schema
$id: sbdb://recipes
title: Recipe
description: A cooking recipe with ingredients, steps, and provenance.

x-entity: recipes
x-storage:
  layout: docs/recipes/{id}.md
  body: markdown
x-id: { property: id, format: kebab-case }
x-integrity: sha256
x-partition: { by: cuisine }
x-events: { emit: [created, updated, archived] }

type: object
additionalProperties: false
required: [id, title, status, cuisine, servings]
properties:
  id:        { type: string, pattern: "^[a-z0-9-]+$" }
  title:     { type: string, minLength: 3, maxLength: 120 }
  status:    { type: string, enum: [draft, active, archived], default: draft }
  cuisine:   { type: string, enum: [italian, japanese, mexican, indian, other] }
  servings:  { type: integer, minimum: 1, maximum: 24 }
  prep_time: { type: integer, description: "Minutes of active prep" }
  author:    { type: string, $ref: "sbdb://people#/properties/id" }
  tags:      { type: array, items: { type: string }, default: [] }
  nutrition:
    type: object
    properties:
      calories: { type: integer, minimum: 0 }
      protein_g: { type: number, minimum: 0 }
    additionalProperties: false
```

About thirty lines, and it earns its keep five times over. `additionalProperties: false` means a typo in a key fails validation — you cannot accidentally introduce `prep_tme` because nothing accepts it. `enum` on `cuisine` collapses six teams' spellings of "japanese / Japanese / jp / JPN" into one canonical token before they ever ship. The `$ref` on `author` points at another schema in the same repo (we will come back to that). The nested `nutrition` object validates as its own shape. And the `default` values mean an author who omits `status` and `tags` still produces a valid record — `sbdb create` fills them in.

The frontmatter that satisfies this schema is unremarkable in the best possible way:

```yaml
---
id: cacio-e-pepe
title: Cacio e Pepe
status: active
cuisine: italian
servings: 2
prep_time: 20
author: marco-rossi
tags: [pasta, quick, classic]
nutrition: { calories: 640, protein_g: 24.5 }
---

The Roman dish that proves three ingredients are enough...
```

This is what the schema costs you: zero. The author writes the same YAML they were going to write anyway, and gets autocomplete, validation, and a refusal-to-save when `cuisine: italyan` slips through.

Two more `x-` keys round out the vocabulary: `x-partition` (a hint for how the index buckets records — by cuisine, by tenant, by week) and `x-events` (which lifecycle events the entity emits into the audit log; Part 6 builds on this). Everything else is plain JSON Schema. If you want to know what a key does, the rule is simple: starts with `x-`, read the sbdb docs; doesn't, read the JSON Schema spec.

## Foreign Keys via `$ref` — One Paragraph

The `author` field in the recipe schema used `$ref: "sbdb://people#/properties/id"`. That URI is two things at once. To a stock JSON Schema validator, it is "go look up the `id` property in the `people` schema and validate against *its* type and pattern." So if `people` says ids are 8-character ULIDs, the recipe's `author` field has to be an 8-character ULID — for free, no extra config. To `sbdb`, the same `$ref` is also a **foreign-key edge** that gets extracted into the knowledge graph at index time. When you query "which recipes does marco-rossi own," the answer comes from a SQLite edge table, not a grep. We will unpack that mechanism in Part 5; for now, the move to remember is that one annotation does double duty — validation *and* relational structure — and that is exactly the kind of leverage you want from a contract.

## What Validation Failure Actually Looks Like

When the schema disagrees with the input, the failure mode is the kind of error message that closes the ticket instead of opening one:

```bash
$ echo '{
  "id": "cacio-e-pepe",
  "title": "Cacio e Pepe",
  "status": "invalid",
  "cuisine": "italian",
  "servings": 2
}' | sbdb create recipes -

ERROR validate recipes/cacio-e-pepe
  /status: "invalid" is not one of [draft, active, archived]
    schema: sbdb://recipes#/properties/status/enum
    fix: set status to one of the listed values, or add the value to the schema

exit code: 2
```

No stack trace, no `panic: interface conversion`, no Go-routine dump. The error reports the JSON Pointer (`/status`), the schema location that rejected it (`sbdb://recipes#/properties/status/enum`), and a one-line fix. The exit code is stable (`2` is always "validation failed") so an AI agent driving the CLI doesn't have to parse English to know what happened — it checks `$?`, sees `2`, and either rewrites the field or appends the new value to the schema and tries again. That stable-exit-code contract is the difference between a tool an agent can use and a tool an agent flips a coin on.

## Schema Evolution — Additive vs Breaking

Schemas drift; that is not a bug, it is the steady state of a real codebase. `sbdb` tracks evolution with `x-schema-version` — a plain integer at the top of the schema. Every schema starts at `1`. **Additive changes don't bump the version**: adding a new optional property, adding a new value to an enum, loosening a `maxLength`. Existing records remain valid because they already satisfy the old constraints. Bump only on **breaking changes**: removing a property, removing an enum value, tightening a type, renaming a key.

The shape of an additive change is boring on purpose:

```yaml
# v1 → still v1; recipes/*.md continue to validate without touching them
x-schema-version: 1
properties:
  servings: { type: integer, minimum: 1, maximum: 24 }
+ difficulty:
+   type: string
+   enum: [easy, medium, hard]
+   default: medium
```

A breaking change ships a migration descriptor in the same PR. `sbdb schema migrate` reads it and walks every record on disk:

```yaml
# v1 → v2; cuisine enum loses "other", gets split into specific cuisines
x-schema-version: 2
x-migrations:
  - from: 1
    to: 2
    actions:
      - rename_enum:
          property: cuisine
          from: other
          to: ask_author
      - require: [difficulty]
properties:
  cuisine:
    type: string
    enum: [italian, japanese, mexican, indian, thai, french, ask_author]
```

`sbdb schema migrate --from 1 --to 2 --dry-run` reports which records would change and why. Without `--dry-run`, it rewrites the frontmatter and emits a migration event into the git log — which means the migration is *itself* a reviewable diff, not a one-time imperative script. The same migration descriptor also handles the legacy `entity:` / `fields:` dialect that early `sbdb` repos used before draft-2020-12 landed; running `sbdb schema migrate --legacy` upgrades the dialect in place.

> The team that runs schemas stops grepping for *"what fields does an ADR actually have?"* and starts treating their knowledge base the way they treat their database migrations — versioned, reviewable, and small enough to read in one breath.

## Schemas Under Review, Like Migrations

The last piece is operational, not technical. Schemas live in `schemas/*.yaml`, alongside the rest of the codebase, and they go through pull request review like any migration. The reviewer is reading thirty lines of YAML; they can hold the whole contract in their head while the author is still talking. A schema PR is the *cheapest* PR in the repo to review well, because the surface is small, the impact is large, and the validator runs in the CI step right next to the lint.

There is even a meta-schema — the schema that describes what a valid `sbdb` schema looks like. It enforces that every entity has an `x-entity`, that `x-id` points at a property that actually exists, that enum lists are non-empty, that `$ref`s resolve. `sbdb schema lint` runs it on every schema in `schemas/` and reports the same shape of error you saw above. The validator that validates the validator: turtles, but only two layers deep.

## What You Get to Stop Worrying About

The team that runs schemas stops grepping for *"what fields does an ADR actually have?"* and starts treating their knowledge base the way they treat their database migrations — versioned, reviewable, and small enough to read in one breath. The 4 a.m. AI agent that decides every recipe needs a `prep_tme` field gets a non-zero exit code and a refusal, not a quiet corruption that you discover six months later when someone tries to count active recipes by cuisine. The new engineer onboarding to the docs repo opens `schemas/` first, reads thirty lines of YAML, and knows the shape of the world before they have read a single document.

That is the future state worth building toward: a knowledge base where the shape is enforced, the vocabulary is shared, and the field names are something you have an opinion about because they appear in PR review next to the code that depends on them. Part 3 turns the camera one layer down — once the *shape* is enforced, can you prove the *bytes* haven't been tampered with? That is the integrity-signing story, and it is what turns "the schema says this is an ADR" into "and here is the cryptographic receipt that the body still says what the author signed."
