# Zero Trust: Secrets When You Trust Nobody (PGP + SOPS)

> Commit real secrets to git — encrypted well enough that the repo can be public. PGP and SOPS for the working engineer, plus an honest map of where the trust boundary actually moves.

**You can commit your production database password to git. Today. In the next ten minutes.** If the repo gets cloned, leaked, scraped, or accidentally made public, anyone who reads it gets exactly nothing — a binary opaque to anyone outside a recipient list you can name on a whiteboard. That sentence is either a firing offence or a Zero Trust architecture, and the difference between the two is a tool called SOPS and a primitive called PGP.

Part 1 was about the head-change — where verification terminates, why the brain alone is a bad root, and why the mature answer is plural rather than singular. This part is the head-change applied to the single most paranoid asset in your repo: the credentials. If the mindset from Part 1 was real, then secrets in git should not feel like a transgression. It should feel like the most auditable place they have ever lived.

## The Mindset

Old rule: *secrets must never touch source control.* That rule exists because most teams ship secrets in plaintext, and source control is forever. Bad combination.

New rule, when you actually adopt Zero Trust: *secrets in source control are fine if a copy of the repo is useless to anyone outside the recipient list.* The encryption is the perimeter — and it is a perimeter you can carry with the file, instead of a perimeter you have to provision around it.

The trust does not vanish, it relocates. You used to trust the storage system: "this database, this vault, this S3 bucket is safe enough to hold the plaintext." Now you trust the *recipient list*: "these three engineers and this CI identity are the only ones who can read this file." The new attack surface is the keyring plus the recipient list — usually one or two orders of magnitude smaller than the surface of the storage system you replaced, and with names you can actually list on a whiteboard.

This relocation is the whole win. The plaintext was never the asset; the *access* to the plaintext was. By making the access controllable per file and per recipient, you push the trust decision down to the smallest unit that matters.

## PGP in One Paragraph

PGP has reputational baggage and most of it is earned. The UX is bad, the key management has historically been worse, and serious cryptographers have written serious essays about why PGP-the-product-family is a mess. None of that touches PGP-the-primitive: asymmetric encryption with native support for many recipients. Each engineer holds a private key, publishes a public key, and any plaintext can be encrypted *once* in a form that any one of the listed recipients can decrypt independently. There is no shared secret to leak. Adding a fourth recipient does not require re-encrypting anything for the original three. That property — multi-recipient envelope encryption — is exactly the shape the problem has. If the baggage bothers you, **age** is a modern alternative that SOPS supports as a drop-in; the architecture in this article is identical with `age` substituted for `pgp` in every config.

## SOPS on Top

PGP alone gives you "encrypt the whole file." Fine for one credential, terrible for a YAML config with thirty values. You lose the diff. You cannot tell from `git log` whether the change was a password rotation or a typo in a hostname.

SOPS is Mozilla's tool that fixes that. It encrypts *only the values*, leaving the keys readable. A `secrets/prod.yaml` looks like this after `sops -e`:

```yaml
database_url: ENC[AES256_GCM,data:bH9...g==,iv:k7Z...,tag:q4d...,type:str]
api_key: ENC[AES256_GCM,data:Lf2...kQ==,iv:HfA...,tag:Yp8...,type:str]
stripe_webhook_secret: ENC[AES256_GCM,data:Mn3...Bw==,iv:VeQ...,tag:Kx7...,type:str]
sops:
    pgp:
        - fp: 9E91ABE3F1F2E1C7E5D2A4F6B8C0D1E2A3F4B5C6
          enc: |
            -----BEGIN PGP MESSAGE-----
            ...wrapped data encryption key for Dev A...
            -----END PGP MESSAGE-----
        - fp: 4B3F9C5A1D2E8F119A0B1C2D3E4F506172839405
          enc: |
            -----BEGIN PGP MESSAGE-----
            ...wrapped data encryption key for Dev B...
            -----END PGP MESSAGE-----
        - fp: AABBCCDDEEFF00112233445566778899AABBCCDD
          enc: |
            -----BEGIN PGP MESSAGE-----
            ...wrapped data encryption key for CI...
            -----END PGP MESSAGE-----
    lastmodified: "2026-05-17T10:00:00Z"
    version: 3.8.1
```

Every value is encrypted with the same per-file *data encryption key* (DEK). The DEK is generated fresh per file. Then the DEK itself is encrypted ("wrapped") once per recipient and stored in the `sops:` trailer. This is the same trick TLS uses for session keys: cheap symmetric encryption for the bulk, expensive asymmetric encryption only for the tiny key that unlocks it.

## The Minimum Viable Workflow

One-time setup, once per engineer:

```bash
gpg --full-generate-key            # pick RSA 4096 or ed25519
gpg --list-secret-keys --keyid-format LONG
gpg --armor --export <FINGERPRINT> > my-pubkey.asc
```

Once per repo, in the repo root, create `.sops.yaml`:

```yaml
creation_rules:
  - path_regex: secrets/.*\.yaml$
    pgp: >-
      9E91ABE3F1F2E1C7E5D2A4F6B8C0D1E2A3F4B5C6,
      4B3F9C5A1D2E8F119A0B1C2D3E4F506172839405,
      AABBCCDDEEFF00112233445566778899AABBCCDD
```

Then the daily verbs:

```bash
sops -e -i secrets/prod.yaml       # encrypt in place
sops -d secrets/prod.yaml          # decrypt to stdout
sops secrets/prod.yaml             # open in $EDITOR, decrypt on open, re-encrypt on save
```

In CI, the build agent has its own key (PGP, or — better — a cloud KMS identity referenced via `kms:` in `.sops.yaml`). The pipeline never writes plaintext to disk. It pipes the decrypted value directly into the process that needs it:

```bash
export DATABASE_URL="$(sops -d --extract '["database_url"]' secrets/prod.yaml)"
./run-migrations
unset DATABASE_URL
```

That sequence — decrypt, use, unset — is the secret-handling equivalent of the "every request, every time" principle from Part 1. The plaintext exists only for the duration it is needed, in the memory of the process that needs it, and nowhere else.

## Onboarding and Offboarding Without Panic

When a new engineer joins, you do not re-encrypt the secret. You add their public key fingerprint to `.sops.yaml` and run:

```bash
sops updatekeys secrets/prod.yaml
```

That command does one thing: it re-reads the recipient list from `.sops.yaml`, re-wraps the existing DEK for the new recipient set, and rewrites the `sops:` trailer. The ciphertext values do not change. The diff in your PR is a few lines at the bottom of the file plus a fresh `lastmodified` timestamp. The reviewer sees exactly one thing happen: a new wrapped-DEK block appeared, this engineer's fingerprint is on it.

When someone leaves, you do the opposite: drop their fingerprint from `.sops.yaml`, run `sops updatekeys`, commit the diff. From that moment forward, files updated under the new recipient list cannot be decrypted by the leaver's key.

A common objection at this point: *the leaver could have kept a plaintext copy from when they had access.* Yes. They could have. That is why for genuinely sensitive secrets — production database passwords, signing keys, customer-data API tokens — you also rotate the underlying secret value, not just the recipient list. The two operations answer different threats. Recipient rotation answers *future* access; secret rotation answers *historical* compromise. For the 90% of secrets where the secret value is cheap to rotate (API keys for third-party services) or low-impact even if leaked (staging databases), recipient rotation alone is the right tradeoff. Make that decision per secret, not as a blanket policy.

## The Trust Boundary That Didn't Disappear

Zero Trust is not "no trust" — it is *minimum trust, made explicit*. With SOPS, three trust assumptions remain and you should be able to name them on demand.

**The recipient list.** `.sops.yaml` is the most security-critical file in the repo. If an attacker can sneak their own key fingerprint in via a PR, every future commit to a secrets file will encrypt to their key as well. Mitigation: branch protection on `.sops.yaml`, required reviews from a named security owner, and a CI check that fails if the recipient list changes outside a designated PR template.

**The CI build identity.** Whatever key your pipeline holds — PGP private key in a vault, KMS role on the build agent — has read access to everything. Treat it as a single point of failure and reduce its lifetime aggressively. A short-lived cloud KMS role tied to a specific repo+branch is much better than a long-lived PGP private key sitting on a Jenkins box.

**The audit log.** You trust that you can answer *who decrypted what, when?* PGP-only setups give you almost nothing here — `gpg --decrypt` does not phone home. SOPS with cloud KMS gives you the cloud provider's audit log for free; every unwrap of the DEK lands as a decrypt call against the KMS key. That log is the difference between "we got breached and we'll know in six months" and "we got breached and we know which file at which minute."

The worst mistake teams make is committing the private keyring alongside the encrypted secrets. The encryption is mathematically correct; the operational hygiene is wrong, and once both halves are in the same git history, you have not done Zero Trust — you have done Caesar cipher on a sticky note. Private keys live in hardware tokens, OS keychains, or cloud KMS. Never in the repo.

## What This Lets You Stop Worrying About

The teams that adopt this stop having the conversation about "where do we put the secrets manager." They stop building bespoke tooling to inject env vars into pods at runtime. They stop the awkward Slack thread asking who has the staging password this week. The repo *is* the secrets manager, and the recipient list *is* the access policy, and the diff *is* the audit log. Three things you used to maintain separately collapse into one artefact that every reviewer already knows how to read.

The engineers who get this right describe the same feeling: secrets stop being a source of operational fear and start being just another part of the codebase you can refactor, version, and review. A new engineer joins, the diff that adds them is three lines and clears review in minutes. A leaver is removed in the same shape. The production password becomes as legible as a hostname, and as safe as a hash.

> The trust boundary moved. It did not vanish. From *everyone with read access to the git host* to *everyone with a private key on the recipient list* — usually one or two orders of magnitude smaller, with names you can recite.

That compression *is* the win, and it is the same compression every Zero Trust pattern in this series is going to produce. Part 3 turns the camera on the history itself: once the secrets are encrypted, can you prove that the *audit trail* has not been tampered with? That is the immutable-stream story — append-only ledgers, hash chains, the past you cannot unhack — and it is what makes everything you have built so far provable, rather than merely true.
