# Comprehension Debt: Metaframework

> Your product management tool is a database your repo has never heard of. Bring the product home — typed, validated, and able to fail CI.

Your product management tool is a database your repo has never heard of. Every decision, every scope cut, every "why" lives in a SaaS silo while your codebase — the thing those decisions describe — evolves alone in git. Bring the product home.

Disclosure before the first argument, because this part needs one: this is a thesis, not a product pitch — but I am building one implementation of the thesis, and I'll show it to you below with its version number, its license, and its day-one limitations attached. The thesis itself is nothing new to this series. It is what [Part 2](/blog/comprehension-debt-frozen-context), [Part 3](/blog/comprehension-debt-boundaries-beat-willpower), and [Part 4](/blog/comprehension-debt-specs-with-a-failing-state) add up to when you follow them all the way down: if a spec deserves a failing state, so does everything you currently trust to a ticket tracker.

## The Last Silo

Consider what already moved. Code was born in version control. CI used to be a Jenkins instance somebody configured by clicking; now it's YAML in the repo. Infrastructure used to be a console and a prayer; now it's Terraform, reviewed like any other diff. Even documentation — with all of Part 2's caveats about what prose can and cannot promise — at least lives in `docs/`, versioned next to the thing it describes.

Every one of those migrations delivered the same three gifts: a diff, a review, a history. You can see exactly what changed, argue about it before it lands, and reconstruct later why it happened. We liked those gifts so much we rebuilt entire job descriptions around them.

Product management is the holdout. The decisions about what the system *is* — which capabilities exist, which journeys matter, which trade-offs were accepted, which payment provider gets the traffic when the primary dies — live in Linear, or Jira, or Notion. A hosted database, reachable through a browser tab, owned by a vendor. No diff. No review gate. A history you can't `git log`. [Naur told us](https://pages.cs.wisc.edu/~remzi/Naur.pdf) back in [Part 1](/blog/comprehension-debt-the-debt-nobody-booked) that the theory of a program can never be fully written down — but the half that *can* be written down, the decisions and boundaries and named invariants, we dutifully write into the one store the repo cannot see.

Your agents feel this daily. They read every file in the repository at machine speed, and the product context — the actual reason the code is shaped the way it is — arrives by copy-paste, paraphrased, three sprints stale.

> Your infra is code. Your pipeline is code. Your product — the reason the other two exist — is a filter view in someone else's database.

## A Word Worth Reclaiming

I'm going to call the fix a metaframework, and the word needs immediate defense, because it's taken. Ask any frontend developer: a metaframework is Next.js or Nuxt — a framework built on top of a framework. That meaning can keep the name; it earned it. The *process* sense of the word, though, is sitting there unclaimed: a framework above your development process. Not a library, not a methodology deck — a governance layer whose job is to hold the catalog of what the product *is*. Components, products, capabilities, journeys, decisions. The nouns. Every tracker ever built manages the verbs — what to do next — and quietly assumes the nouns are in somebody's head.

The neighbors sharpen the definition. [GitHub's Spec Kit](https://github.com/github/spec-kit) is the loudest of them, and it is deliberately *ephemeral*: spec, plan, and tasks scaffold one feature, then retire when it ships. [OpenSpec](https://github.com/Fission-AI/OpenSpec) is the closest neighbor — durable specs plus reviewable change deltas — but it's prose all the way down: no types, no schemas, nothing a machine can reject. Backlog.md and claude-task-master put work items in git, which is progress, but a to-do list in the repo is still a to-do list; it describes the work, not the architecture the work produces.

A metaframework in this sense is the missing quadrant: durable rather than per-feature, about the product rather than about the tasks — and, critically, checkable rather than merely readable.

## The Four Properties

Parts 2 through 4 each ended by handing this part a requirement. Collected, there are four.

**Stable addressing.** [Part 2's](/blog/comprehension-debt-frozen-context) drift problem has a quieter cousin: even when prose is true, it isn't *citable* — every reader re-interprets the narrative on every read. The research on agent-native artifacts is blunt about what reasoning needs: [stable, citable units](https://arxiv.org/html/2604.24658), not stories. So every entity gets a URI — `srn://billing/checkout/adr/psp-fallback` — solution, product, component path, kind, name. An address that survives file moves is an address an agent can cite in a commit message. It's also how [context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) gets its smallest-possible set of high-signal tokens: resolve one address, load one entity, skip the other forty pages of knowledge base.

**Typed entity kinds.** [Part 3's](/blog/comprehension-debt-boundaries-beat-willpower) boundary argument, applied to knowledge. An entity declares what it is — component, product, capability, journey, ADR, protocol — and its kind constrains what it may claim. A type is a boundary on a document.

**Per-kind schema validation.** Each kind carries a JSON Schema for its frontmatter. An ADR without a status isn't a style problem; it's invalid, the way a function call with a missing argument is invalid.

**A CI gate.** [Part 4's](/blog/comprehension-debt-specs-with-a-failing-state) entire thesis, inherited directly: the check must exit 1. This is the frozen knowledge base of Part 2 re-armed — same markdown, same git, plus the one property markdown never had. A failing state.

## One Implementation, Honestly

Now the disclosed part. [@bershadsky/metaframework](https://github.com/sergio-bershadsky/metaframework) is my implementation of the above — v0.1.0, published yesterday, licensed PolyForm Noncommercial, production adoption approximately one team, and I'm on it. None of that is false modesty; those are the honest coordinates of a young tool, and the thesis does not depend on this particular tool winning.

What it does: entities are markdown files with typed frontmatter in a `solutions/` tree; each kind carries a JSON Schema; `metaframework check` validates the whole catalog and exits 1 on the first lie; and a zero-runtime-dependency portal serves the tree as a live site, re-reading a 288-entity catalog in about 239 ms on change. The design constraint behind all of it fits in one sentence: the filesystem is the database, your editor is the editor, git is the history.

An entity is nothing exotic:

```markdown
---
kind: adr
name: psp-fallback
status: accepted
supersedes: srn://billing/checkout/adr/psp-retry@1
---
Route traffic to the fallback PSP after two primary timeouts inside 30s.
```

And when a refactor renames the superseded ADR, or a hurried edit fat-fingers a field, the gate is exactly as boring as Part 4 promised a good gate should be:

```text
$ metaframework check
FAIL solutions/billing/checkout/adr/psp-fallback.md
  supersedes: srn://billing/checkout/adr/psp-retry@1 does not resolve
  status: "acepted" is not one of [proposed, accepted, superseded]
2 errors in 1 entity — exit 1
```

Evolution is additive-only: a breaking change to an entity means a new version at a new address, with the old one marked superseded — never rewritten in place. That is the discipline that keeps addresses stable, and it's borrowed directly from how you already treat published API versions.

Equally important is what the tool refuses to do. No browser-side writes — the portal is read-only, and edits go through your editor and a pull request, because the review flow *is* the feature. No auth — access to the repo is access to the catalog, the end. No plugin system yet — Part 3 made the case for contracts before extensions, and I intend to take my own advice.

> v0.1.0 means what it says. It validates, it serves, it says no in CI. That is the entire résumé.

## Product Review Becomes Code Review

Play a scope cut through this machinery. Someone opens a PR that edits a capability entity, marks one journey descoped, and adds a superseding ADR explaining why. Reviewers see a diff — the actual delta of the product, not a comment thread. CI runs the check and confirms every address still resolves and every kind still validates. The merge *is* the decision, and `git log` is the paper trail. Six months later, "when did we drop guest checkout, and why" is not an archaeology expedition across four tools — it's `git blame` on a file with a schema.

The agents change character too. In Part 1's second figure, the agent had no write path to the right-hand side — the theory lived only in heads, and everything the machine touched sat on the left. This is the missing write path, or the closest thing to one that doesn't require telepathy: agents cite `srn://` addresses instead of paraphrasing stale prose, propose entity edits by pull request like any other teammate, and when one cites an address that doesn't exist, the gate catches it — not somebody's memory, three weeks later, in an incident review.

I won't overclaim, because [Naur](https://pages.cs.wisc.edu/~remzi/Naur.pdf) remains undefeated: the full theory still can't be serialized, and no catalog will hold the conversation that produced a decision. But the writable half of the theory — the decisions, the boundaries, the invariants that Part 1 showed walking out the door with every resignation — can finally live where everything else you trust already lives. A repo where product intent, architecture, and code share one history, one review flow, and one failing state is a repo where the theory has a durable home outside heads — readable by juniors, citable by agents, and guarded by a gate that says no. Whether you get there with my one-day-old tool or with a folder of schemas and a fifty-line validator you write yourself, the four properties are the point; any implementation of them is just Tuesday's answer. What to do first, second, and third — starting Monday, with the repo you already have — is [Part 6](/blog/comprehension-debt-the-monday-playbook).
