# Zero Trust: Immutability as Proof

> Append-only streams, hash chains, and the past you cannot unhack. The third trust shift: stop trusting the storage layer to be honest about its own history.

**Your database does not have rows. It has a present hallucination of rows, recomputed every query from a stream of events the storage layer politely hid from you.** The truth was never in the cell. The truth was in the log, and the log is the only thing an attacker cannot quietly edit without telling you.

Once you stop treating *current state* as primary and the *event stream* as derived, three things become possible that were not possible before. You can prove the past is intact. You can replay it to any moment. And you can do both without trusting the storage layer to be honest about itself. Part 1 was about where verification terminates. Part 2 was about how to keep secrets when nobody is trusted, including yourself. This part is about *time itself* — the property that makes everything you built in the first two parts auditable rather than merely true.

## State Is a Fold Over Events

Functional programmers have been quietly correct about this for forty years. The current state of any system is not a fundamental thing. It is `fold(initial_state, events)` — what you get when you replay the history from the beginning, applying each event in order. The database row that says `balance: $500` is not a fact. It is a *cached projection* of a stream that goes `+$200, +$350, −$50, …`, and the storage layer hides the stream from you for performance reasons that have nothing to do with truth.

Most production systems hide this so well that engineers come to believe it is not there. The row is what is in the cell. The cell is the system. *What history?*

> A relational database is an event stream that has gone to great lengths to convince you it is a filing cabinet. The filing cabinet abstraction is fast and ergonomic and almost true. The almost is where the breach lives.

When you flip the mental model — when state becomes the *derived view* and the event log becomes the *source of truth* — every operation in your system gains a property it did not have before: it is *attributable*. Every change to the balance has a row in the log that says *who, when, how much, why*. The "current state" is then a function of the log, not a thing maintained alongside it. The breach scenario where an attacker quietly changes a cell becomes impossible without also changing the log entry that produced that cell — and that change, as we will see in a moment, is loud.

## You Are Already Doing This — Git

The first time most engineers internalise this idea is the day they realise that *git is already a hash chain*. Every commit references the hash of its parent. Modify any commit anywhere in the history — change a byte, fudge an author name, alter a timestamp — and every descendant commit's hash changes. The tampering is loud rather than silent. The graph itself becomes the proof.

```bash
git log --pretty=format:"%h %p %s" --max-count=5
# 9dc61a9 1ccdf46 Remove _redirects; SPA fallback handled by wrangler not_found_handling
# 1ccdf46 7729c82 Add wrangler.jsonc for Cloudflare Workers Static Assets deploy
# 7729c82 f07577c Remove server/; consolidate to static-only
# ...
```

Read it as a chain, not a list. Each commit hash is a function of its content *plus* its parent hash. You have been using a tamper-evident ledger to manage your code for fifteen years and probably never described it that way. The property the rest of this article wants to give your *data* is the property git already gives your *source*.

> Git is what would have happened if cryptographers had designed source control. They did, eventually. We just called it Linux Torvalds being annoyed at BitKeeper, but the substance was the same.

This is why "your favourite tool already proves the property we want for everything else" is not a metaphor. The mechanism is identical. You have lived with it. You have trusted it. The leap to immutable application data is the leap to using the same primitive for a different payload.

## Hash Chains in One Paragraph

A hash chain is the simplest construction that turns *append-only* into *tamper-evident*. Every block has three fields: the event data, the hash of the previous block, and its own hash computed as `H(prev_hash || event_data)`. Flip one bit anywhere — in any event, in any past block — and the hash of that block changes. Which changes the `prev_hash` of the next block. Which changes its own hash. Which propagates forward until the head of the chain. The bit-flip cannot stay local. It announces itself.

A working example, in ten lines of Python:

```python
import hashlib

def chain_link(prev_hash: str, event: str) -> str:
    return hashlib.sha256(f"{prev_hash}|{event}".encode()).hexdigest()

events = ["deposit:200", "deposit:350", "withdrawal:50"]
chain = ["GENESIS"]
for e in events:
    chain.append(chain_link(chain[-1], e))

# tamper with event #2 in retrospect:
events_tampered = ["deposit:200", "deposit:9999", "withdrawal:50"]
chain_tampered = ["GENESIS"]
for e in events_tampered:
    chain_tampered.append(chain_link(chain_tampered[-1], e))

print(chain[-1] == chain_tampered[-1])   # False — heads diverge
```

The two heads do not match. If you have published or pinned the original head — to a signed checkpoint, a notarised hash, a peer's copy of the chain — the tampering is detectable by anyone who has that head and a copy of the events. Nothing about this requires blockchains, distributed consensus, mining, or any other ceremonial machinery. It is just a hash function and an append-only file.

## Streams in Real Systems

You rarely build a hash chain by hand. The systems you already use either provide one, or can be configured to behave as one.

**Kafka as the durable append log.** Kafka topics are append-only by design; consumers read by offset; retention can be set to *infinite* (or compaction can preserve the last value per key without losing the tombstones). Treat the topic as the system of record and your relational store as a materialised view, and the relational store stops being the place where your truth lives. It becomes a cache.

**Event sourcing for application state.** Every state-changing operation is an *event* persisted before any view is updated. The aggregate's current state is computed by replaying its events. CQRS pairs this with a separate read-side projection so queries stay fast. Frameworks: Axon, Eventuous, EventStoreDB; or your own append-only Postgres table with an `event_at` column and a strictly monotonic sequence. The framework is not the point. The discipline of *write the event first, derive the state from it* is the point.

**Append-only object stores.** S3 Object Lock and GCS retention locks give you write-once-read-many semantics enforced *by the cloud provider*. Even an attacker with admin credentials cannot rewrite or delete a locked object before its retention period expires. Use this for the artefacts that *must* survive a breach: audit logs, signed checkpoints, recovery snapshots.

Three different scales of the same idea. Pick whichever costs you the least to retrofit. The first one you adopt unlocks the next two.

## Proving Non-Tampering to an Outsider

A hash chain proves to *you* that the past is intact. To prove it to an outside party — an auditor, a regulator, a customer — you need two more primitives.

**Merkle trees** compress an arbitrarily long log into a single 32-byte hash, the *Merkle root*. The root summarises every event in the log: change anything, anywhere, and the root changes. The auditor verifies a specific event by asking for the *Merkle proof* — a logarithmically-sized sequence of sibling hashes that lets them recompute the root themselves. They never read the whole log. They never trust your servers. They re-derive the root from the proof, compare it to the published root, and either it matches or you have some explaining to do.

**Signed checkpoints.** Periodically — every minute, every hour, every block — sign the head hash of the chain with a key the auditor knows. Anchor that signature somewhere out-of-band: a public log, a tamper-evident bulletin board, a counterparty's S3 bucket with their own retention lock. Now an attacker who alters the past must not only re-compute every downstream hash but also forge every checkpoint, on every external anchor, in every timestamp. The cost of the attack stops being *local to your infrastructure*.

The honest aside: blockchains are the public-distributed-consensus version of this primitive. They are *one* instantiation, expensive and ceremonial, and almost never the right first reach for a single-tenant system. Hash chains, Merkle trees, and signed checkpoints get you 95% of the property without paying the consensus tax.

## The 3 a.m. Question

Eventually you will get breached. Statistically, anyone running real systems long enough will. The interesting question is not *can you prevent it*; the interesting question is *what does the post-mortem look like*.

In the state-first world: at 3 a.m. you wake up to a Slack ping. A row in the production accounts table is wrong. *You think.* You're not sure when it changed, or whether it was the only one, or whether the change you're looking at now is the original tampering or a partial cleanup attempt. The forensics meeting starts with someone saying *"let's pull what we have from the backups,"* and ends six hours later with a sentence containing the words *"we believe."*

In the stream-first world: at 3 a.m. you wake up to the same Slack ping, but it does not say *"a row is wrong."* It says *"chain broke at block 4,712 — head hash diverged from the signed checkpoint at 02:14:08."* You open the audit tool, it shows you the exact event that started the divergence, the events downstream, the signed checkpoints that did and did not validate, the recipient identities that touched the chain around that timestamp. The forensics meeting starts with *"here is the smallest interval that contains the breach,"* and the post-mortem ends with the words *"we know."*

The engineers who internalise this stop fearing breaches the way they used to. Not because breaches stop happening — they do not — but because the panic of *not knowing* is replaced by the work of *reading the chain*. The chain is loud. The chain is legible. The chain is the architecture making good on a promise it made you at design time, which is the promise every layer of Zero Trust is making in its own register: that the past is something you can prove, not something you have to hope about. Part 4 takes the next question down the stack — once you can prove the past, *how do the workloads inside it get an identity in the first place?* — and that is where SPIFFE earns its place.
