# Comprehension Debt: Specs With a Failing State

> A spec that can't fail is an opinion with a heading. The industry put $125M and 93k GitHub stars behind fixing that.

A spec that can't fail is an opinion with a heading. The industry finally noticed — and put $125M and 93,000 GitHub stars behind the fix. The next artifact you write should be able to go red.

That's the shout; here's the survey to back it. [Part 2](/blog/comprehension-debt-frozen-context) ended at a fork: generate docs *from* code, or generate code *from* specs. Follow either road far enough and you arrive at the same building — a document wired to a checker, where the direction of the arrow is a design choice but the presence of a gate is not. [Part 3](/blog/comprehension-debt-boundaries-beat-willpower) applied that logic to architecture; this part applies it to intent. By the end you'll be able to place every tool in the spec-driven wave on one map, know which camp it belongs to, and know the minimum honest setup for a codebase that already exists — because you were never going to rewrite it for someone's manifesto.

## An Opinion With a Heading

Strip the vendor language and a spec is three things: a document, a runner, and an exit code. Something machine-shaped reads the document, compares it against reality, and is authorized to say no. Remove any leg of that tripod and you're back to documentation — which, as [Part 1](/blog/comprehension-debt-the-debt-nobody-booked) established, captures conclusions while the theory stays in heads, and as Part 2 established, drifts into fiction precisely because nothing breaks when it lies. The test to apply to anything calling itself a spec is short: *what goes red when this stops being true?*

The mechanism is much older than the current wave. Doctests put the example inside the documentation and executed it — lie in the docstring, fail the build. Cucumber scenarios and OpenAPI contract tests industrialized the same move: [one artifact that reads as explanation and evaluates as a contract](https://ai-assisted-software-development.com/executable-specs/). These were always the most trustworthy documents in any codebase, for exactly one reason: they were the only ones that could be wrong in a way a machine could catch. Contrast the agent-rules literature's own concession that [loading an ADR into a prompt is not enforcing it](https://www.actual.ai/blog/agent-optimized-adrs) — informing and binding are different operations, and only one of them survives contact with a system that changes daily.

> Documentation asks to be believed. A spec agrees to be tested.

What's new in 2025–26 is not the mechanism. It's that the industry stopped treating executable documents as a testing technique and started treating them as *the writing format for intent*. That shift produced two camps.

## Camp One: Docs From Code

Cyrille Martraire's [*Living Documentation*](https://www.infoq.com/articles/book-review-living-documentation/) is the mature statement of the first camp, and it predates the agent era entirely. The thesis: most documentation dies because it's a manual copy of knowledge that already lives in the code — so stop copying. Derive the docs from the code, its annotations, its tests, and its build output, as a side-effect of the build itself. A glossary generated from the domain model cannot forget a renamed concept. A dependency diagram generated from the import graph cannot show the module you deleted in May. The knowledge is coupled to the artifact that changes, so drift isn't discouraged — it's structurally impossible.

The camp's honest limit is the direction of its arrow. Generated docs can only describe what the code already does; they cannot state what the system *should* do before it does it. That makes camp one a fine repayment instrument for the comprehension debt you already carry — a theory-rebuilding aid that never lies — but it has nothing to gate generation with. The agent ships whatever it ships, and the living docs faithfully describe the damage: truthful, current, and entirely without an opinion on whether any of it was a good idea.

## Camp Two: Code From Specs

The second camp flips the arrow: make intent the durable artifact and code the output. This is where the money and the stars went, in roughly eighteen months.

[GitHub's Spec Kit](https://github.com/github/spec-kit) — 93,000+ stars as of this writing — is the most visible. Its pipeline is a four-phase ritual: a *constitution* of project principles, then `/specify`, `/plan`, and `/tasks`, each phase generating the markdown the next phase consumes, with the agent finally [implementing against the spec and plan](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/) rather than against a vibe in a chat box. GitHub's framing is the movement's thesis sentence: we're moving from "code is the source of truth" to "intent is the source of truth."

AWS's Kiro made the shape of intent concrete. Every Kiro spec generates [three files — requirements, design, tasks](https://kiro.dev/docs/specs/) — and the acceptance criteria in the first are written in [EARS notation](https://kiro.dev/docs/specs/feature-specs/requirements-first/): `WHEN [event] THE SYSTEM SHALL [behavior]`. Whatever you think of the syntax's charm, it is testable by construction — every criterion sits one WHEN away from being a check.

[OpenSpec](https://github.com/Fission-AI/OpenSpec) is the smallest of the three and, for this series, the most interesting: a persistent `specs/` directory holding current truth, a `changes/` directory holding *delta-specs* — proposed modifications to that truth — and a validator that fails hard in strict mode. It's the only one whose central object is a long-lived spec corpus rather than per-feature scaffolding.

At the maximal end sits [Tessl](https://tessl.io/blog/tessl-launches-spec-driven-framework-and-registry), which [raised $125 million](https://techcrunch.com/2024/11/14/tessl-raises-125m-at-at-500m-valuation-to-build-ai-that-writes-and-maintains-code/) to pursue the full inversion: the spec becomes the source artifact and code a regenerable build output, recompiled from intent the way binaries are recompiled from source. One skeptical aside, as promised: that's a bold bet to place while the entire industry still reviews code diffs by hand, and I'd treat it as a bearing, not a destination. Around the authoring edge, [BMAD](https://github.com/bmad-code-org/BMAD-METHOD) attacks the upstream problem with role-specialized planning workflows that produce the spec documents in the first place.

> It took $125 million to make "documents should be able to fail" a fundable thesis. Cheap, honestly, for a sentence the industry spent forty years not writing down.

Read the fine print, though, and each tool enforces less than its landing page implies. Spec Kit enforces *process order* — its templates are markdown, and the checker is mostly you. Kiro enforces the *shape* of requirements. OpenSpec enforces the *structure* of change — its validator rejects malformed deltas but cannot evaluate their wisdom. Nobody yet enforces semantics end to end. That's not a dismissal; normalizing the gate is the achievement. But it tells you where the map still has blank regions.

## What the Agents Changed

Why did a forty-year-old mechanism suddenly acquire venture funding? Because agents changed which artifact is scarce. When implementation is cheap to regenerate, code stops being the thing you'd grieve losing; the intent that can regenerate it is. That's the [spec-driven pitch](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/) in one move: the spec is the durable artifact the agent executes against, gets verified against, and reports against — the half of the loop that survives the session.

But camp two conceals a fork that matters more than any feature list: what happens to the spec *after* the feature ships. Spec Kit's specs are ephemeral — per-feature scaffolding that does its job and retires to a folder nobody re-reads, taking its acceptance criteria with it. Which lands you back in Part 2's problem at a higher altitude: a pile of expired intent, frozen at merge time. OpenSpec's answer is the persistent alternative — a living corpus mutated only by validated deltas, where the `specs/` directory *is* current truth and every change re-earns its green. And once you notice that a persistent, validated, addressable spec corpus is starting to look like a typed product catalog under CI, you've noticed the door [Part 5](/blog/comprehension-debt-metaframework) walks through.

> The agent holds no opinion about your beautiful spec. It has an exit code to satisfy — which is already more accountability than your wiki ever offered anyone.

## The Minimum Viable Failing Spec

None of this requires adopting a manifesto, an IDE, or a registry. For a codebase that already exists, the entry price is two moves.

**Gate the seams you already have.** Your API boundary almost certainly has an OpenAPI file that has been quietly lying since some Tuesday nobody remembers. Wire a contract test to it and it becomes the first document in the building with a failing state — the [doctest move](https://ai-assisted-software-development.com/executable-specs/), applied to the doc your consumers actually depend on. You are not writing new truth; you are arming the truth you already have.

**Delta-specs on new work only.** Don't spec the legacy mass — gate the margin. Every new feature gets a small spec with scenario structure, validated in CI with a hard exit code. The ratchet does the rest: a year from now, the actively-changing parts of the system are exactly the parts under spec, because coverage followed change instead of chasing it.

Here's what the gate looks like when it earns its keep:

```bash
$ openspec validate add-rate-limits --strict

Validating changes/add-rate-limits...
ERROR  requirement "Reject requests over the limit"
       has no scenario block - criterion is untestable
ERROR  delta targets spec 'api/rate-limiting'
       which does not exist in specs/
FAIL   2 errors, 0 warnings - exit code 1
```

That failure is the entire product. Ten lines of terminal output just converted "what does rate limiting actually mean here" from a recurring meeting into a build failure — settled asynchronously, by whoever fixes the paragraph, before a single line of implementation existed. A red spec is disagreement surfacing at validate-time, when it costs a rewrite of prose; the alternative is disagreement surfacing at incident-time, when it costs a weekend and a retro.

This is the possibility the whole movement is circling. When the spec is the thing that fails, arguments about what the system should do stop being scheduled and start being *caught* — and the document becomes the first one your team has ever owned that grows more trustworthy as the system grows, because every green run re-earns it. Writing intent down precisely was never the hard part. Getting an honest answer to "is this still true?" was — and now a machine volunteers that answer on every push, for free. Start with one seam and one delta-spec this sprint, and let the ratchet compound. The next artifact you write should be able to go red. So should the next one you read.
