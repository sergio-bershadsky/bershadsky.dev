# SBDB: The Knowledge Graph

> Foreign keys for markdown — typed `$ref` edges, prose-link edges, a local SQLite index, and reverse-link queries in milliseconds.

**Your docs already form a graph. Every `[link](other-doc.md)` is an edge, every `$ref` is a foreign key, every "see also" line is a relationship the human encoded and the tooling discarded.** `sbdb` reads the same files and turns the graph into a thing you can *query* — `who links to this ADR?`, `which notes mention this decision?`, `give me every doc that is two hops from the auth-rotation incident` — in milliseconds, from a SQLite index that sits next to the markdown and rebuilds on every write.

Two ingredients do the work: JSON-Schema `$ref` pointing at `sbdb://<entity>#/properties/<id>` for *typed* foreign keys, and a link-extractor over the markdown body for *prose* edges. Both flow into one SQLite database that `sbdb query` reads on every command. The rest of this part is a tour of that pipeline — what it stores, what it does not, and the small catalogue of traversals worth memorising.

## The Graph That Was Always There

Open any healthy team wiki and look at it sideways. The pages are nodes, the inline `[deploy runbook](runbooks/deploy.md)` references are edges, the "Related ADRs" section at the bottom of every decision document is a hand-rolled adjacency list. The graph is *already there*. It has been there since the first engineer typed two square brackets and committed.

The tooling, however, treats the graph as decoration. Confluence renders the link as blue text. Notion renders it as a backlink — sometimes. Git treats the file as an opaque blob. None of them can answer the question every engineer has at 3 a.m.: *what else points at this thing I am about to delete?*

> Every wiki you have ever used knows how to render a forward link and forgets how to follow a backward one. That is not a feature gap. That is the entire problem.

`sbdb` takes the same view a relational database takes of a CSV directory: the relationships are not metadata, they are first-class rows. The link extractor walks each `.md` body, parses the frontmatter, follows every `$ref` in the schema, and writes a row into `edges(from_id, to_id, kind, source_field)` for every relationship it finds. Then it indexes the whole thing. Then it forgets nothing.

The crucial move is treating the markdown file as the *only* source of truth and the SQLite index as a disposable projection. Delete the index and `sbdb index` will rebuild it from the files in under two seconds. Corrupt the index and the worst case is a rebuild. The graph is never the canonical record; it is a lens for asking questions, and a lens you throw away and re-grind every time the underlying glass changes.

## Typed Foreign Keys via `$ref`

The cleanest edges are the ones the schema declares. JSON Schema 2020-12 gives us `$ref` for free, and `sbdb` extends it with a custom URI scheme — `sbdb://<entity>#/properties/<id>` — that points at another entity's primary key. The validator treats the value as a string; the indexer treats it as a foreign key.

```json
{
  "$id": "sbdb://decisions",
  "type": "object",
  "properties": {
    "id":      { "type": "string", "pattern": "^adr-\\d{4}$" },
    "title":   { "type": "string" },
    "status":  { "enum": ["proposed", "accepted", "superseded"] },
    "supersedes": {
      "type": "array",
      "items": { "$ref": "sbdb://decisions#/properties/id" }
    },
    "owner":   { "$ref": "sbdb://people#/properties/id" },
    "incident": { "$ref": "sbdb://incidents#/properties/id" }
  },
  "required": ["id", "title", "status"]
}
```

Four kinds of edge are declared here without a single line of imperative code. The `supersedes` array creates `decision → decision` edges of kind `supersedes`. The `owner` field creates one `decision → person` edge of kind `owner`. The `incident` field, when present, ties the ADR to the post-mortem that triggered it. The schema is the place where relationships are *declared*, not described — and the indexer can hydrate the entire graph just by walking the type tree.

The payoff is the same one ORMs always pitch: integrity checks. An ADR that references a non-existent incident is a validation error before it is a runtime mystery. `sbdb doctor` will flag the dangling edge the next time it runs, and the offending file will not pass `sbdb check` until the reference is healed. The relationship becomes part of the file's *type*, not part of its prose, and the validator treats a missing target the way a compiler treats a missing import.

The other benefit is that the relationship gets a name. A `$ref` in the `supersedes` field is unambiguously a supersession; a `$ref` in `owner` is unambiguously an ownership tie. The query layer can ask `sbdb links --kind supersedes` and get back precisely the decision-replacement chain — no string matching on the title, no fragile regex on the body, no convention that depends on the engineer who wrote it remembering the convention.

## Prose Edges From Inline Links

The schema cannot catch everything. Half the most useful relationships in a knowledge base live in the body of the prose: *"this was originally proposed in [the November design review](meetings/2025-11-12.md)"*, *"see also [the rotation runbook](runbooks/key-rotation.md) for the operational steps"*. Those links carry intent that no schema field was ever going to declare in advance.

So `sbdb` runs a second pass — a markdown link extractor that walks every `[text](path)` in the body and, if the path resolves to another tracked entity, writes an edge of kind `mentions`. The `text` becomes the edge label; the source field is recorded as `body` so the query layer can distinguish prose links from schema-declared ones.

```markdown
---
id: adr-0042
title: "Rotate auth signing keys quarterly"
status: accepted
supersedes: [adr-0017]
incident: inc-2025-11-08
---

This decision came out of the [auth-rotation incident](../incidents/inc-2025-11-08.md).
See also [the rotation runbook](../runbooks/key-rotation.md) and the long thread in
[the November design review](../meetings/2025-11-12.md).
```

```sql
-- After sbdb index, the edges table now contains:
-- (one row per discovered relationship)
INSERT INTO edges (from_id, to_id, kind, source_field, label) VALUES
  ('adr-0042', 'adr-0017',           'supersedes', 'frontmatter.supersedes', NULL),
  ('adr-0042', 'inc-2025-11-08',     'incident',   'frontmatter.incident',   NULL),
  ('adr-0042', 'inc-2025-11-08',     'mentions',   'body',                   'auth-rotation incident'),
  ('adr-0042', 'rb-key-rotation',    'mentions',   'body',                   'the rotation runbook'),
  ('adr-0042', 'mtg-2025-11-12',     'mentions',   'body',                   'the November design review');
```

Notice the duplicate row pointing at `inc-2025-11-08` — one schema-declared, one prose-mentioned. The graph keeps both, because losing the prose mention loses the *reason* the link was made.

> A prose edge is a schema edge with feelings. The schema knows the type of the relationship; the prose remembers why the human bothered to write it down.

## SQLite Under the Hood

The whole index lives in a single file — `.sbdb/index.sqlite` — sitting next to the markdown. This is not a graph database. There is no Cypher query planner, no PageRank, no clustering on a Kubernetes node nobody remembers provisioning. It is three tables (`entities`, `edges`, `entity_fields`) and four indexes, served from the same SQLite that powers your iPhone's contacts app.

There are reasons for this choice and reasons against it. The reasons for: SQLite ships everywhere, requires no daemon, is faster than every network round-trip a real graph database needs, and serialises to a single file that can be `.gitignore`d and rebuilt on demand. The reasons against: it is a single-machine index, joins are bounded by SQL's recursion limits, and at the upper end — somewhere past ten thousand documents and a million edges — you will start to feel the rebuild cost on cold-cache writes.

For the workloads `sbdb` is aimed at — engineering team ADRs, runbooks, design docs, customer-incident records — those bounds are nowhere on the horizon. The largest knowledge base I have tested it on, a Frappe-customisation team's six-year archive, is 3,400 documents and 28,000 edges, and `sbdb index` rebuilds the whole thing from scratch in 1.3 seconds. The breakpoint that matters is the one your team will *never reach*.

> A knowledge base is not Twitter. If you ever genuinely need a Neo4j cluster to traverse your engineering wiki, congratulations — your real problem is that you write too much.

What `sbdb` stores: every entity's primary key, every field value flat-indexed for `--filter`, every edge with its `from`, `to`, `kind`, `source_field`, and optional `label`. What it does not store: the prose body itself (the markdown file is the source of truth — re-read it when you need it), computed virtual fields beyond their cache TTL, and anything the schema did not declare or the link extractor could not resolve.

## The Query Surface

Three commands cover ninety percent of the daily use. `sbdb query` reads entities by property. `sbdb links` reads edges by direction. `sbdb path` finds the shortest hop sequence between two nodes. Everything else is composition.

```bash
$ sbdb query --filter status=accepted --filter incident=inc-2025-11-08 \
    --entity decisions --format json
[
  {
    "id": "adr-0042",
    "title": "Rotate auth signing keys quarterly",
    "status": "accepted",
    "supersedes": ["adr-0017"],
    "owner": "p-aanand",
    "incident": "inc-2025-11-08"
  }
]
```

The `--filter` flag is variadic and AND-composed. Predicates run against the flat `entity_fields` table — string equality by default, prefix on `~`, numeric ranges on `<`/`>`. There is no query language to learn; the surface is the same as a `find` command, and it is meant to feel that way.

The edge queries are where the graph repays the investment. `sbdb links --from adr-0042` lists every outbound edge. `sbdb links --to inc-2025-11-08` answers *the question every wiki refused to answer* — who points at this thing? At a depth of two, you get the neighbourhood: every doc the focal node mentions, and every doc *those* docs mention.

```bash

  "depth": 2,
  "nodes": [

The further you walk, the muddier the relevance — which is exactly why most useful queries top out at depth two.

## The Reverse-Link Superpower

Forward links are easy. Every tool ever built can render `[click here](there.md)`. The interesting question, the one your wiki has been ducking for years, is the *reverse*: when I am looking at `inc-2025-11-08`, what else in this knowledge base talks about it?

On a real engineering knowledge base, this is the query that changes what people *do* — because for the first time, deleting a doc is something you can do with eyes open. You see what points at it, you decide whether the link survives the rewrite, and you commit. The graph is no longer a metaphor.

> A backlink query is the difference between *"I think we discussed this somewhere"* and *"we discussed this in seven places, here they are."* One of those is a feeling. The other is a knowledge base.

## What This Lets You Stop Worrying About

You stop losing context when a teammate leaves. You stop deleting docs that something important still depends on. You stop searching for the conversation that led to the decision, because the decision document is literally connected to the conversation, by an edge, in a row, in a file you can read. You stop maintaining a hand-curated "Related" section at the bottom of every page, because the graph already knows. You stop being the person who answered *"where did we talk about that?"* at every standup for a year, because every engineer with a terminal can ask the database that question and get the same answer you would have given them, faster than you would have given it.

The engineer who finally has a real knowledge graph stops asking *"where did we discuss that?"* and starts asking *"show me everything two hops out from that decision"* — and getting an answer in the time it takes to read the question. The wiki you grew up with promised you this for fifteen years and quietly failed to deliver. `sbdb` does not promise it. It just writes the rows, indexes the columns, and lets the graph speak. The next part of the series turns the same trick on time — every commit in your repo becomes a row in an audit log, and the history you wrote with `git log` becomes a stream of events your tooling can subscribe to.
