# SBDB: Virtual Fields

> Stop typing the title twice. Starlark virtual fields compute frontmatter from the markdown body — sandboxed, deterministic, and loud when they lie.

The title of your document is already in the file — it's the first `# heading`. Maintaining it as a separate `title:` frontmatter field that you type a second time and then forget to update is the kind of human-managed redundancy that knowledge bases are made of, and it's the reason your dashboard says "Untitled" for half of them. `sbdb` lets you declare *virtual fields* — properties computed from the markdown body by a sandboxed Starlark function — so the title, the word count, the JIRA-ticket references, the step count, and anything else derivable from the content stop being something a human maintains.

A virtual is just a property with `readOnly: true` and an `x-compute` block; Starlark is Python's quiet, deterministic, sandboxed cousin, and ten lines of it covers ninety percent of the cases. The rest of this part is recipes, the boundary of the sandbox, and what the schema does when a virtual lies about its type.

## The drift problem

Frontmatter and body are written by the same human in the same editor, one above the other, and they still drift apart. The body gets edited; the `title:` line on top stays frozen from the day the file was first created. The list of section anchors goes stale within a week. The `word_count` was honest once, six months ago. The JIRA tickets referenced in the body are not in the `tickets:` list because nobody re-runs grep when they add a paragraph.

> Every field a human has to maintain in two places will, on a long enough timeline, disagree with itself.

Part 2 of this series made the case for typed frontmatter — `title` must be a string, `tags` must be an array of enums, `status` must be one of four values. That's necessary. It is not sufficient. Type-checking a value that was wrong the moment it was typed does nothing for the truth of the file. The schema can prove your `word_count` is an integer; it cannot prove it is *the right* integer. The fix isn't more validation. The fix is to stop asking the human for the value at all.

There's a long folklore of half-solutions to this — pre-commit hooks that rewrite the YAML, editor plugins that update a sidebar on save, GitHub Actions that fail a PR when the title doesn't match the H1. They all work for about three weeks. They all collapse the moment someone edits the file outside the blessed toolchain, or the hook is bypassed in a hurry, or the plugin stops being maintained. The information was always derivable from the body. What changes with virtuals is that the derivation lives *inside the schema*, runs at every write, and is not optional.

## The fix in one line

A virtual field is a regular schema property with two extra things:

1. `readOnly: true` — the schema declares the field is not human-editable. `sbdb` refuses writes from the outside and will *overwrite* anything a human pastes in.
2. `x-compute:` — a small block that names a Starlark function. On every write, `sbdb` calls `compute(content, fields)` and stores the result back into the frontmatter.

That's it. The virtual sits in the same schema as every other property. It type-checks like every other property. It indexes into the knowledge graph (Part 5) like every other property. From the outside it's indistinguishable from a hand-maintained field — except it's right, every time.

The `title` virtual fits in ten lines of schema and three lines of Starlark:

```yaml
title:
  type: string
  readOnly: true
  x-compute:
    language: starlark
    function: |
      def compute(content, fields):
          for line in content.splitlines():
              if line.startswith("# "):
                  return line[2:].strip()
          return "Untitled"
```

The function takes the markdown body and the rest of the frontmatter (`fields`), walks until it finds the first H1, returns the text. If there is no H1 it returns `"Untitled"` — and because `title` is declared `type: string`, the schema is happy. The day someone renames the H1 in the body, the next `sbdb write` rewrites the frontmatter `title:` line for free. No grep, no script, no reminder.

## The catalogue

Five virtuals that earn their keep on day one of any real knowledge base. Copy them.

**`word_count`** — the simplest case, one expression:

```yaml
word_count:
  type: integer
  readOnly: true
  x-compute:
    language: starlark
    function: |
      def compute(content, fields):
          return len(content.split())
```

That's the whole feature. Your archive page can now sort by length, your "five-minute reads" filter actually works, and nobody had to type a number.

**`jira_refs`** — a regex over the body, deduplicated, sorted:

```yaml
jira_refs:
  type: array
  items: { type: string, pattern: "^[A-Z]+-[0-9]+$" }
  readOnly: true
  x-compute:
    language: starlark
    function: |
      def compute(content, fields):
          matches = re.findall(r"[A-Z]+-[0-9]+", content)
          return sorted({m: True for m in matches}.keys())
```

The same pattern works for GitHub issues (`#\d+`), RFCs (`RFC-\d{4}`), CVEs, customer IDs — anything with a regular shape that authors will absolutely forget to list in frontmatter. The `items.pattern` in the schema means the *output* is type-checked too: if some clever Starlark refactor produced `"auth-1421"` in lowercase, the schema rejects the write. The virtual cannot lie to the index.

**`last_section`** — the title of the final `## heading`. Useful when "where did this document end up" is a queryable property of your runbook collection. Incomplete documents stop at `## Background`; finished ones reach `## Rollout`. A weekly query for "all runbooks whose `last_section` is not in {`Rollout`, `Verification`, `Rollback`}" turns into a quiet, honest backlog of half-written things without anyone tagging anything.

**`step_count`** — count of `1.` / `2.` numbered list items at the start of a line. Lets a runbook collection sort by length-in-steps rather than length-in-words, which is closer to how humans actually feel the cost of executing one. A four-step runbook and a forty-step runbook are different products; the schema can now know that.

**`title`** — already covered above. The single highest-ROI virtual in the catalogue. If you adopt exactly one virtual in your knowledge base, adopt this one. The reduction in "Untitled" rows alone justifies the entire feature.

> A good virtual is a one-line answer to "what does grep already know that my frontmatter pretends not to?"

## The sandbox

Starlark looks like Python and it isn't. That's the point. The Starlark interpreter `sbdb` embeds has no filesystem, no network, no `import`, no `subprocess`, no clock with sub-second resolution, no source of nondeterminism. The standard library it exposes is small on purpose: `re` for regex, `string` operations, `dict` and `list`, `len`, `sorted`, `range`, `enumerate`. That's about it.

The restriction is the feature. A virtual is, by construction, a pure function of `(content, fields)`. Run it twice on the same input and you get the same output. That property is what makes the materialised frontmatter cacheable, what lets `sbdb doctor` (Part 3) verify that the stored frontmatter matches what would be recomputed, and what means a hostile or buggy virtual cannot exfiltrate data, talk to your CI's IAM role, or `rm -rf` anything. There is no IO surface. The worst a malicious virtual can do is return a string the schema rejects, and the write fails closed.

> Starlark is the smallest language that lets you do useful work and the largest you'd let a teammate paste into a config file you both have to live with.

Cross-document context is *deliberately* unavailable. A virtual cannot read the file next door. If you want a property derived from other documents — backlinks, reference counts, "how many runbooks cite this ADR" — that lives in the knowledge graph (Part 5), not in a virtual. Virtuals are local. The graph is global. Keeping those two clean is what stops the system from collapsing into "spreadsheet, but bigger."

The author who has only ever written Python will trip on this exactly once. They'll reach for `import datetime` to stamp something, hit a parse error, mutter something unkind about toy languages, and then notice — about thirty seconds later — that the very thing they were about to do is exactly the thing the sandbox is refusing to let them do. The constraint is the design. A virtual that depends on the wall clock is not a function of the body; a virtual that imports the network is not a function of anything you can audit. Five minutes of friction here saves a year of "why is the title field different in production than in CI."

## When the virtual lies about its type

The schema declares `word_count: integer`. The Starlark author writes:

```yaml
word_count:
  type: integer
  readOnly: true
  x-compute:
    language: starlark
    function: |
      def compute(content, fields):
          return str(len(content.split()))   # accidental str()
```

The next time anyone runs `sbdb write` on a document that uses this schema:

```
$ sbdb write docs/adr/0042-oidc.md
error: virtual field 'word_count' produced wrong type
  schema declares:  integer
  starlark returned: string ("214")
  file:    schemas/adr.yaml
  field:   word_count
  at:      docs/adr/0042-oidc.md
write rejected; no changes on disk
```

The failure is loud, at write time, with the offending file and field named. The on-disk document is untouched — `sbdb` writes the file and the integrity sidecar (Part 3) atomically, so a rejection means nothing moved. There is no silent half-write to clean up, no half-indexed graph row to garbage-collect, no "the frontmatter says it's an integer but the sidecar hash disagrees" stale state to chase next quarter.

## When not to use a virtual

Virtuals are seductive, and the temptation is to make everything computed. Three cases where the answer is no.

**Fields that need history.** `author`, `created_at`, `last_reviewed_by`. These are facts about *events*, not the current state of the body. A virtual recomputed from `content` cannot know who first wrote the H1, or which reviewer approved the third revision. That's git's job (Part 6), or a normal hand-set frontmatter field, never a virtual.

**Fields that need cross-document context.** "How many other ADRs cite this one." "Which runbooks reference this service." A virtual cannot read the document next door — by design. That answer comes from the knowledge graph in Part 5, computed at query time, never frozen into a frontmatter field.

**Fields the user explicitly wants to edit.** `summary`, `pitch`, `one_liner`. There is a long, sad lineage of tools that tried to compute "the summary" from the body and produced something the author would never have written. If the field is editorial, leave it editorial. `readOnly: true` is for facts; opinions stay writable.

> The rule of thumb: if you'd be willing to delete the field and rebuild it from scratch on every write, it's a virtual. If not, it isn't.

## Frontmatter the author stops thinking about

The win, at the end of all this, is small and quiet. The author writes the document. The H1 is the title because the H1 was always going to be the title. The word count is honest because nobody had to maintain it. The JIRA tickets in the index match the JIRA tickets in the body because the index is derived from the body, not typed alongside it. The frontmatter block at the top of the file stops being a chore the author has to remember and starts being something that appears, correctly, the moment they save.

A knowledge base that does this stops needing the weekly cleanup script, the quarterly metadata audit, the "please remember to update the front-matter" reminder in the PR template. The metadata is a function of the content, and the content is what the author was going to write anyway. That's the shape every long-lived knowledge base eventually wants, and most teams build it from spreadsheets and shame. `sbdb` lets you build it from ten lines of Starlark and call it done.

Part 5 turns the camera on the connections *between* documents — foreign keys, link extraction, the queryable graph that virtual fields cannot reach. Once the inside of each file is honest, the next thing the system can answer for you is what each file knows about its neighbours.
