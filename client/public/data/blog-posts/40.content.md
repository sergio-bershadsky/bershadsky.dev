# SBDB: Integrity Signing

> Per-file hashes, three flavours of drift, and a `doctor` command that makes silent edits loud. The third part of the secondbrain-db series.

**Someone is going to edit a frontmatter field by hand. An AI agent is going to silently drop three fields on a rewrite. A merge conflict resolver is going to "fix" the YAML in a way nobody reviews. With `sbdb` integrity signing on, *all three are loud* — every file carries a hash sidecar, every mutation refreshes it, and the moment a byte drifts without authorisation, `sbdb doctor` lights up red.**

The mechanic is small — a sidecar file per doc with a content hash and a schema version — but the consequence is large: knowledge becomes *provably unchanged since you last looked at it*. One quick clarification before we go further. The audit log (Part 6) records every authorised mutation as a git commit, *per-event*. Integrity signing is the orthogonal axis: *per-file*, telling you whether the bytes on disk match what `sbdb` last wrote. Different question, different mechanism, different failure mode.

## Knowledge Bases Rot Quietly

The honest reason most engineering wikis are wrong is not that anyone lied. It is that everyone was busy. A teammate fixes a typo in a runbook and skips the review. An agent on a feature branch rewrites the front-matter to "normalise" a tag enum. Six months later a different teammate reads the doc, treats it as canonical, and ships a decision built on a sentence that was never reviewed by a human who understood it.

The thing that makes this insidious is the *silence*. Files don't ring a bell when they change. Git tracks the change, but only if the change was committed — and the failure modes that hurt most happen *between* commits, in the working tree, in the agent loop, in the merge resolver's three-second pause.

> A wiki is a database where every row is also a stochastic variable. The schema tells you what a recipe is supposed to look like. The hash tells you whether anyone has been quietly redefining "recipe" while you weren't watching.

`sbdb` does not solve this with discipline. Discipline is what failed. It solves it with a hash sidecar and a `doctor` command that runs on every read, every write, and — if you wire it up — every end-of-turn from your AI agent. The contract is unsexy and stubborn: if a byte changes in a tracked file without `sbdb` knowing, *something* tells you, before that byte becomes the basis of someone's decision.

To be precise about what this is *not*: it is not a defence against a determined attacker who has write access to your repo. They will edit the file *and* the sidecar and you will be none the wiser. That problem is solved one layer up, by branch protection and signed commits. What integrity signing catches is the much larger, much more frequent category of failure — the accidental edit, the impatient agent, the rushed merge. The mistakes by people on your side of the firewall, which is where the rot actually comes from.

## The Sidecar

Every doc that lives under an `x-integrity`-enabled schema gets a sidecar. By default it lives next to the file (`.<filename>.sbdb`); in projects that prefer a clean working tree it lives under `.sbdb/integrity/<entity>/<id>.json`. Same payload either way:

```json
{
  "content_hash": "sha256:9e3c4f8b1d72a6c5e0b2f9a4d8c1e5b7a3f6d2c8e4a9b1d5c3f7e2a8b4d6c1e9",
  "schema_version": "recipes/v3",
  "last_seen": "2026-05-15T14:32:08Z",
  "writer": "sbdb@0.9.4",
  "fields_normalised": ["tags", "ingredients[*].unit"]
}
```

Five fields, no more. `content_hash` is SHA-256 over the canonicalised file contents — frontmatter re-emitted in stable key order, body trimmed of trailing whitespace, line endings normalised to `\n`. `schema_version` pins the doc to the schema that was active when `sbdb` last wrote it (so a schema migration shows up as drift if you forget to bump). `last_seen` is the timestamp of the last successful write or healed read. `writer` is the binary version that wrote the sidecar — useful when the canonicaliser itself changes between releases. `fields_normalised` lists which keys `sbdb` rewrote on its last pass, so you can answer "did the tool change the file, or did a human?" without staring at a diff.

The hash is not crypto-grade signing. It is *drift detection*. An attacker with write access to your repo can edit the file and edit the sidecar and you will never know — that is what git commit signatures, branch protection, and the audit log are for. The sidecar's job is the much smaller, much more frequent problem: *did anyone change this file in a way `sbdb` didn't ratify*?

## Three Drift Modes

The interesting part of integrity signing is not the hash. It's the *taxonomy of drift* that the hash reveals. Real teams produce three flavours; `sbdb doctor` learned to name them because the response differs.

**Hand-edit drift.** Someone opens the markdown in their editor and fixes a typo, or rewrites a sentence, or — most commonly — adds a tag because they were closing the loop on a meeting. The file changes; the sidecar does not. `doctor` reports the file as drifted, shows the byte diff, and asks: do you want to re-hash (accepting the human's edit as canonical) or revert (treating it as unintended)? Hand-edits are the friendliest drift mode. A human is in front of the keyboard. The right answer is almost always *re-hash and move on*.

**Agent rewrite drift.** An AI agent — yours, mine, the one your teammate is letting loose during lunch — was asked to "update the recipe section" and decided that meant rewriting the front-matter too. Three fields are gone, one was renamed, the body is mostly intact. The hash is shot. Worse, `fields_normalised` in the sidecar shows the agent didn't go through `sbdb` at all — it edited the file directly, then exited. This is the drift mode the project is really aimed at. The fix is a Stop-hook (see below) that runs `sbdb doctor heal --all` at end-of-turn and re-validates everything against the schema.

**Merge-conflict resolution drift.** A teammate resolved `<<<<<<<` markers in a doc and committed. The bytes on disk are now a frankenstein of two branches. Each branch's sidecar matched its branch's content; neither matches the merged result. `doctor` flags this with `cause: merge_residue` and refuses to auto-heal — because in a merge case, "rewrite the sidecar to match the file" is silently endorsing a resolution that *no human reviewed*. The correct human action is to read the merged doc, confirm it says what you wanted, then `sbdb doctor heal <path>` explicitly.

## `doctor check` vs `doctor heal`

Two verbs, two postures.

`sbdb doctor check` is the read-only one. It scans the tracked directory, recomputes every hash, compares against every sidecar, and emits a JSON report with one entry per drifted file. Wire it into your CI; fail the build on any non-empty report. It is the answer to *"did our knowledge base survive this PR intact?"* without anyone arguing about the diff.

```json
{
  "checked": 412,
  "drifted": 1,
  "issues": [
    {
      "path": "recipes/dal-tadka.md",
      "cause": "content_hash_mismatch",
      "schema": "recipes/v3",
      "expected": "sha256:9e3c4f8b…1e9",
      "actual":   "sha256:7d2a9c1e…4b2",
      "fields_changed": ["body", "tags"],
      "advice": "run `sbdb doctor heal recipes/dal-tadka.md` after review"
    }
  ]
}
```

`sbdb doctor heal` is the mutating one. It accepts a path (or `--all`), reruns the canonicaliser, rewrites the sidecar, and — if the file's frontmatter still validates against its schema — declares the new state canonical. Crucially, `heal` *refuses* on `cause: merge_residue` unless given `--force`; `sbdb` would rather make you angry than silently bless a merge nobody reviewed. The two-verb split matters: `check` is what CI runs, `heal` is what humans (or trusted hooks) run with their eyes open.

## The Stop-Hook Story

If you have an AI agent editing files in your repo — Claude Code, Cursor, Aider, your own scaffold — integrity signing earns its keep at the end of every turn. The agent does what agents do: opens files, rewrites passages, sometimes touches frontmatter. The Stop-hook fires when the turn ends and runs a single command:

```bash
sbdb doctor heal --all --schema-validate --quiet || sbdb doctor check --all
```

If `heal` succeeds, integrity is back in lockstep and the next turn begins on a clean base. If `heal` fails because the agent introduced a schema violation, `check` prints the report and the agent sees its own damage in its next prompt window. *That feedback loop is the whole point.* The agent learns, in the same way a human linter teaches you, that frontmatter is a contract and not free verse. You keep the speed of AI-driven authoring; you lose the silent rot.

The reason this works at all is that the hook runs *after* the agent thinks the turn is done. The agent is no longer optimising for a goal; the hook's output becomes part of the next turn's context, not the current one's reward. There is no incentive for the agent to game it. It either touched files cleanly or it did not, and the next prompt makes that visible. Three or four turns into a session, agents that ignore the contract become agents that fix the contract first, because that is the path of least friction. The hook is a teacher whose lesson plan happens to be a JSON diff.

## `x-integrity` — Three Postures

Per-schema, you choose how loud `sbdb` is when drift shows up. The schema fragment is small:

```yaml
$id: recipes/v3
x-integrity: strict
x-integrity-canonicalisation:
  frontmatter_key_order: alpha
  body_trailing_whitespace: trim
  line_endings: lf
```

Three postures, three trust boundaries. `strict` (the default, and what you want for anything load-bearing — ADRs, runbooks, incident records) treats drift as a build failure: CI fails, the agent retries, the human is forced to look. `warn` emits the drift to logs but exits zero — useful exactly twice: while you are *migrating* a corpus onto sbdb and don't want a wall of red on day one, and for genuinely advisory schemas (e.g. scratch notes) where churn is the point. `off` disables sidecars entirely, which is the right answer for schemas where the file is itself disposable and the hash overhead is wasted work.

> "Warn" is the cigarette of integrity settings. It feels like a reasonable middle ground until you realise you have been in the middle ground for eighteen months and never went back to strict.

If you remember one thing from this article, make it this: pick `strict` for everything you would be sad to silently lose, accept `warn` only as a temporary migration scaffold, and ban `off` from anything more important than personal notes. The mechanism is so cheap that the only reason to disable it is fear of the noise on day one — and the noise on day one is the noise you have been ignoring for years.

## What You Stop Worrying About

The team that wires `sbdb doctor heal` into their PR pipeline stops fearing the words *"who edited that?"* They answer with a diff and a hash, not a guess. The agent that runs the Stop-hook stops introducing silent regressions; the next time it touches the same file, it inherits a clean base and learns from its own failed validations. The knowledge base stops drifting — not because nobody edits it, but because every edit registers, and every unregistered edit is loud.

That is the future state worth building toward: a wiki that knows its own state, an agent that gets corrected by the contract rather than the human, a Monday standup where nobody asks whether the runbook on the screen is the one from Friday. The hash sidecar is unglamorous infrastructure. So is plumbing. The houses without it are the ones we don't visit twice. Part 4 takes the next layer — once you trust the bytes, what can you *compute* from them? — and that is where Starlark virtual fields turn read-only frontmatter into a small, sandboxed programming language.
