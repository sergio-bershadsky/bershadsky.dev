# Comprehension Debt: Frozen Context

> Your knowledge base is a snapshot of a theory nobody re-verifies. Markdown can't fail — and that's precisely why it drifts into fiction.

You wrote the CLAUDE.md. You wrote the ADRs. Your agents read them, your juniors praise them — and every word is quietly turning into fiction. Markdown is the only artifact in your stack that cannot fail, and that is exactly what's wrong with it.

I say this as someone who built the knowledge base first and believed in it. It was the obvious response to [Part 1's problem](/blog/comprehension-debt-the-debt-nobody-booked): if the theory lives only in heads, write the theory down — one markdown tree, readable by humans, loadable by agents. And it works, genuinely, for a while. This part is about the ceiling you hit next, why the whole industry hit it simultaneously, and the single property that separates documentation from a contract.

## Everyone Built the Same Thing

The convergence is remarkable when you line it up. OpenAI proposed [AGENTS.md](https://agentsmd.io/agent-md-vs-agents-md) as a "README for agents"; by December 2025 it was donated to the Linux Foundation alongside MCP, read natively by 25+ tools, present in [60,000+ public repos](https://pnote.eu/notes/agents-md/). Anthropic's CLAUDE.md does the same job with a three-layer memory hierarchy. Cline formalized the maximal version as the [Memory Bank](https://docs.cline.bot/best-practices/memory-bank) — explicitly "a methodology, not a feature": a markdown tree the agent re-reads every session to "rebuild its understanding." Cursor scoped its rules files per-path. Even ADRs got retrofitted with [glob-scoped frontmatter so each decision loads only for the files it governs](https://www.actual.ai/blog/agent-optimized-adrs).

Different vendors, one architecture: **serialize the team's theory into prose, keep it in the repo, inject it into every context window.** And to be fair to all of us who built one — the honeymoon is real. A good KB is the best onboarding artifact a team can own. It's the only medium that holds *rationale*, which code cannot express. And it's equally legible to a junior engineer and an LLM, which no other artifact in your stack manages.

> A markdown KB is the perfect employee: knows everything, never objects, never mentions that half of what it knows stopped being true in March.

The problem isn't the idea. The problem is what the artifact *is*: a snapshot. Naur told us in Part 1 that theory degrades on serialization. The KB is that degraded serialization — frozen at the moment of writing, while the thing it describes keeps moving.

## Three Laws of Decay

The decay isn't one failure mode; it's three, and they compound.

**Context rot.** The naive fix for a growing KB is "load more of it." The data says the opposite. [Chroma's Context Rot study](https://research.trychroma.com/context-rot) tested 18 frontier models — GPT-4.1, the Claude 4 family, Gemini 2.5, Qwen3 — and found performance degrades non-uniformly as input length grows, even on tasks a model handles perfectly at short lengths. [Drew Breunig catalogs the four ways this bites](https://www.dbreunig.com/2025/06/22/how-contexts-fail-and-how-to-fix-them.html): poisoning, distraction, confusion, clash. This is why [Anthropic's own context-engineering guidance](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) defines good context as the *smallest possible* set of high-signal tokens — and why [Karpathy calls the whole discipline](https://x.com/karpathy/status/1937902205765607626) "the delicate art and science of filling the context window with just the right information." A fat KB isn't a bigger asset. Past a threshold, it's a liability you pay for per token.

**Rules bloat.** The instruction files rot in a special way: they only ever grow. Every incident adds a rule; no rule ever gets deleted, because nobody is sure it's safe to. Teams auditing bloated CLAUDE.md files find [the agent eventually starts ignoring rules wholesale, not selectively](https://getunblocked.com/blog/audit-fix-bloated-claude-md/) — the file crosses from "guidance" to "noise floor" without any observable event marking the transition.

**Drift.** The quietest law and the fatal one. The KB describes the code, but nothing couples them. Here's the shape of it, from a repo I won't name because it's every repo:

```markdown
# CLAUDE.md — written in March
- All database access goes through `lib/db.ts`.
- We use REST; do not add GraphQL.
```

```typescript
// July. The code moved on. Nothing failed.
import { db } from '@/lib/data/client';      // lib/db.ts deleted in May
const result = await gql(ProjectsQuery);     // GraphQL shipped in June
```

Four months, two load-bearing facts inverted, zero errors raised. Every reader of that KB — human or agent — now *learns falsehoods with confidence*.

## No Failing State

Here's the property that explains all three laws at once. Every other knowledge-carrying artifact in your stack has a **failing state**. Code that lies about types won't compile. Tests that lie go red. An OpenAPI spec that lies breaks the contract test. A Rust doctest that lies fails the build. Each of these artifacts is *forced back into agreement with reality* by a gate that can say no.

Markdown has no such gate. It is prose all the way down: no compiler, no runtime, no assertion. When it lies, the render is identical to when it tells the truth. Even the agent-ADR literature, which is bullish on docs-for-agents, concedes the point in one sentence: [loading an ADR into a prompt is not enforcing it](https://www.actual.ai/blog/agent-optimized-adrs). The prose *informs*; nothing *binds*. Research on agent-native artifacts lands on the same distinction — reasoning needs [stable, citable units, not narrative that must be re-interpreted every read](https://arxiv.org/html/2604.24658).

> Trust is a cache. Every stale fact a reader catches is a cache invalidation — and after enough of them, nobody reads the cache at all.

That's the institutional endgame, and it's the same one your `docs/` folder already went through once, pre-AI: the team stops trusting the KB, stops reading it, then stops writing it. Except now there's a twist — the agents *keep* reading it, at machine speed, with total confidence, long after the humans have quietly written it off.

## The Two Escape Routes

The industry has noticed, and the responses sort cleanly into two camps that agree on the diagnosis and disagree on the direction of the arrow.

**Camp one: generate docs *from* code.** This is Cyrille Martraire's [Living Documentation](https://www.infoq.com/articles/book-review-living-documentation/) thesis, pre-dating agents by years: knowledge you can't trust is worse than none, so derive it — from code, annotations, and build output — as a side-effect of the build, so it *cannot* drift. Doctests, BDD scenarios, and OpenAPI contract tests are the working precedents: [the same artifact reads as explanation and evaluates as contract](https://ai-assisted-software-development.com/executable-specs/).

**Camp two: generate code *from* specs.** Flip the arrow: make the spec the durable artifact and the code the output. That's [GitHub's Spec Kit](https://github.com/github/spec-kit) (constitution → spec → plan → tasks), AWS's Kiro, [OpenSpec's delta-specs with strict validation](https://github.com/Fission-AI/OpenSpec), and — at the maximal end — [Tessl's bet that code becomes a regenerable build product](https://tessl.io/blog/tessl-launches-spec-driven-framework-and-registry).

Notice what both camps quietly agree on: **the fix is a verification loop.** Neither one says "write better markdown and try harder." Discipline is not a mechanism — it loses to any opponent that ships at machine speed, and your opponent now does.

## What Survives the Thaw

So is the KB dead? No — and this is where the nuance earns its keep. Prose remains the only medium that carries *rationale*: the why, the rejected alternatives, the war story behind the invariant. No schema will ever hold that, and a team that deletes its narrative layer has amputated its memory. What dies is markdown *as the enforcement layer* — the pretense that a document that cannot fail can be a source of truth.

The way out is a division of labor. Narrative keeps the why. **Structure** — module boundaries, contracts, typed entities — takes over the what, because structure can be checked by machines that never get tired. Part 3 starts there, with an argument that will sound familiar to anyone who's run a plugin ecosystem: boundaries beat willpower, and a contract you can enforce is worth ten conventions you can only hope for. Imagine opening your KB two years from now and trusting it the way you trust a green build — not because everyone was diligent, but because lying in it makes something, somewhere, go red. That's buildable. The next three parts are the how.
